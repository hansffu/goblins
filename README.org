#+title: Goblins

* EXPERIMENTAL · AI-GENERATED SOFTWARE

*Created for me, by me (and my agent).*

This is a personal experiment, built with substantial AI-generated code. It is made for my own workflow, not a polished or supported product. Expect bugs, breaking changes, and rough edges. The sandbox is experimental too: it has not had an independent security audit. Use it at your own risk.

* What is Goblins?

Goblins runs shells and coding agents (Codex, Claude Code) in Linux sandboxes, called /goblins/. A goblin starts with a small, fixed set of packages. When it needs another tool, it asks for it:

#+begin_src sh
goblin request-package jq --reason "Parse the API response"
#+end_src

You approve or deny the request in a terminal UI or in Emacs, and an approved package appears inside the running sandbox at once, without restarting it.

Around that, Goblins provides:

- *Named configurations* you declare in Nix (=shell=, =claude=, =codex=, ...), each with its own packages, files, environment and network policy.
- *Agent integration*: Codex and Claude Code run with sandbox-only hooks and skills, so they know how to request packages, start helpers and message each other.
- *Scopes*: trust groups of goblins sharing a network, caches and optionally a rootless Docker engine.
- *Flake dev shells*: start a goblin inside a project's =nix develop= environment, and approve changes to it.
- *Nix access* (=allowNix=): a goblin can run ordinary =nix= commands against the host's Nix daemon instead of requesting packages (see [[file:docs/USAGE.org::*Nix in a goblin][Nix in a goblin]]).
- *Host commands* (=hostCommands.enable=): a goblin can ask to run a command on the host, outside its sandbox, once you approve it (see [[file:docs/USAGE.org::*Host commands][Host commands]]).
- *Raids*: goblins group into raids to message each other, and a raid's owner can run more goblins into it.
- *Emacs integration*: approvals, a workspace with each goblin's terminals, and TRAMP access to files inside sandboxes.

A few terms used below:

| Term          | Meaning                                                                      |
|---------------+------------------------------------------------------------------------------|
| configuration | A named, reusable Nix definition, such as =shell= or =claude=                    |
| goblin        | One running sandbox, started from a configuration                            |
| agent name    | The goblin's name, such as =snikk=; chosen with =--name= or picked at random     |
| server        | The background daemon that owns every goblin; run by your normal user        |
| scope         | A named group of goblins that share a network, storage and optionally Docker |

* Requirements

- x86_64 Linux. Goblins has only been tested on NixOS.
- Nix with flakes enabled.
- Unprivileged user namespaces and a recent kernel (it uses =openat2=, =open_tree=, =mount_setattr= and =move_mount=).
- For scopes and Docker: =newuidmap=/=newgidmap= and at least 65536 subordinate IDs for your user in =/etc/subuid= and =/etc/subgid=. NixOS provides these for normal users.

Run Goblins as your normal user, never as root.

* Install

Goblins is configured in Nix: =mkGoblins= builds a =goblins= command that knows your configurations. Add the flake input to your NixOS configuration:

#+begin_src nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    goblins.url = "github:hansffu/goblins";
  };

  outputs = inputs@{ nixpkgs, ... }: {
    nixosConfigurations.your-host = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      specialArgs = { inherit inputs; };
      modules = [ ./configuration.nix ./goblins.nix ];
    };
  };
}
#+end_src

Then declare your goblins in a module, here =goblins.nix=:

#+begin_src nix
{ inputs, pkgs, ... }:
let
  inherit (inputs.goblins.lib.x86_64-linux) builders commonTools;
  inherit (builders) mkGoblins mkGoblin mkClaudeGoblin mkCodexGoblin;
in
{
  environment.systemPackages = [
    (mkGoblins {
      goblins = {
        # An interactive Fish shell.
        shell = mkGoblin {
          pkg = pkgs.fish;
          binName = "fish";
          args = [ "--interactive" ];
          allowedPackages = commonTools;
        };

        # Claude Code, using your existing ~/.claude for login and settings.
        claude = mkClaudeGoblin {
          claudeConfigDir = "$HOME/.claude";
          allowedPackages = commonTools ++ [ pkgs.ripgrep ];
        };

        # Codex, using your existing ~/.codex.
        codex = mkCodexGoblin {
          codexConfigDir = "$HOME/.codex";
          allowedPackages = commonTools;
        };
      };
    })
  ];
}
#+end_src

Rebuild with =sudo nixos-rebuild switch --flake .#your-host=. This installs the =goblins= command and its Fish, Bash and Zsh completions. It installs no service; you start the server yourself.

To change a configuration later, edit it and rebuild. New and changed configurations are used by the next =goblins run=, without restarting the server; running goblins keep the configuration they started with.

** First run

From the project directory you want to work in:

#+begin_src sh
goblins server start   # background server; survives closing the terminal
goblins tui            # approval interface
#+end_src

In another terminal, from the same directory:

#+begin_src sh
goblins run shell --name snikk
#+end_src

Inside the sandbox, request a package, approve it in the TUI, then use it:

#+begin_src fish
goblin request-package cowsay --reason "Try a live package grant"
cowsay hello
#+end_src

The directory you start a goblin in is shared with it read-write, at the same path, so the goblin's edits are your files. In the TUI, Tab switches between sandboxes and requests, =y= / =n= approve or deny the selected request, and =q= closes the TUI while goblins keep running.

To try Goblins from a checkout without configuring anything, =nix shell .#dev-goblins= puts a =goblins= with demo configurations on =PATH= (see [[file:docs/README.org][the developer docs]]).

* Configuring goblins

=mkGoblin= takes the entry program and what the sandbox may access:

| Option                           | Meaning                                                                          |
|----------------------------------+----------------------------------------------------------------------------------|
| =pkg=, =binName=                     | Package and executable to run (required)                                         |
| =args=, =env=                        | Arguments and environment variables; values are literal, not shell-expanded      |
| =description=                      | One line shown to users and agents                                               |
| =allowedPackages=                  | Packages available at startup; defaults to =commonTools=                           |
| =rwDirs=, =rwFiles=, =roDirs=, =roFiles= | Host paths bound into the sandbox, read-write or read-only; =$HOME= and =~/= work    |
| =allowedDomains=                   | =null= (default): open internet; =[]=: no network. Domain filtering is not supported |
| =injectedFiles=                    | Files placed read-only under =/etc= inside the sandbox                             |
| =scope=, =allowedScopes=, =docker=     | See [[*Scopes][Scopes]] and [[*Docker][Docker]]                                                            |
| =allowNix=, =hostCommands=           | Ordinary =nix= commands; approved commands on the host. See [[file:docs/USAGE.org::*Nix in a goblin][Nix in a goblin]] and [[file:docs/USAGE.org::*Host commands][Host commands]] |
| =allowedRunTargets=                | See [[*Raids][Raids]]                                                                         |

The rest of the home directory inside a sandbox is private and temporary. See the [[file:docs/USAGE.org::*Nix API][Nix API reference]] for all options and limits.

** A goblin for developing Goblins

The =goblins-dev= demo goblin (=nix/demo-goblins/=) is set up for working on Goblins itself: Claude Code with =allowNix= and =hostCommands.enable=, in a =goblins-dev= scope whose storage keeps =$HOME/.cargo= and =$HOME/.cache/nix= between sessions, and =claude= and =codex= as run targets, which join that scope. To use the same setup from your own configuration, copy that goblin and =nix/demo-goblins/scopes.nix=; without the scope, Cargo and the Nix fetcher download everything again in every session. See [[file:docs/USAGE.org::*Nix in a goblin][Nix in a goblin]].

** Codex and Claude Code

=mkCodexGoblin= and =mkClaudeGoblin= accept the =mkGoblin= options and add:

- A writable mount of your agent config directory (=codexConfigDir=, default =$HOME/.codex=; =claudeConfigDir=, default =$HOME/.claude=), so the agent uses your existing login. The directory must exist. Use a string, not a Nix path, or your credentials would be copied into the Nix store.
- Hooks and skills mounted only inside the sandbox, under =/etc=. They teach the agent to request packages, enable Docker, run other goblins into its raid and exchange messages. Your own agent configuration is not modified.
- =codexSettings= / =claudeSettings= for extra sandbox-only agent settings, for example =codexSettings.model_reasoning_effort = "high";= or =claudeSettings.model = "sonnet";=.

- =bypassPermissions = true;= to run the agent without its own permission prompts: Claude Code with =--dangerously-skip-permissions=, Codex with the approval policy =never=. It is off by default, and then Goblins asks for no bypass: the agent's own settings decide, such as =permissions.defaultMode= in your Claude settings or =claudeSettings=, or =approval_policy= in your Codex config or =codexSettings=.

Goblins is the sandbox either way, so Codex always runs with =--sandbox danger-full-access= (its own sandbox cannot run inside a goblin). That makes Codex's default approval policy, =on-request=, leave asking to the model: without bypass, Codex rarely prompts, while Claude Code's default mode asks before each tool that changes something. Details: [[file:docs/USAGE.org::*Codex configuration][Codex]], [[file:docs/USAGE.org::*Claude Code configuration][Claude Code]].

Until this option, the agents always bypassed their prompts; a configuration that wants that now sets =bypassPermissions = true;=.

* Scopes

A scope is a named trust group. Its members share:

- one network namespace, so services on =localhost= are reachable across them;
- by default one PID namespace;
- managed storage directories, such as a Gradle or Maven cache;
- optionally one rootless Docker engine (see [[*Docker][Docker]]).

Each goblin keeps its own packages, environment and files. Use a scope when several goblins work on the same project and should share caches or services.

Declare scopes on =mkGoblins= and choose them on each goblin:

#+begin_src nix
mkGoblins {
  scopes = {
    work = mkScope {
      persistent = true;                     # keep storage while no member runs (default)
      storage.gradle.path = "$HOME/.gradle"; # mounted there in every member
      storage.m2.path = "$HOME/.m2";
      docker.enable = true;
      # Defaults for every member; each goblin can add to or override them.
      defaults.allowedPackages = [ pkgs.gradle pkgs.jdk21 ];
    };
    scratch = mkScope { persistent = false; docker.enable = true; };
  };
  goblins.shell = mkGoblin {
    pkg = pkgs.fish;
    binName = "fish";
    scope = "work";                 # default scope
    allowedScopes = [ "scratch" ];  # goblins run shell --scope scratch
  };
}
#+end_src

=mkScope= is in =inputs.goblins.lib.x86_64-linux.builders=, like =mkGoblin=.

- A goblin joins at most one scope, chosen when it starts: its =scope=, or =goblins run CONFIG --scope NAME= for a scope in its =allowedScopes=. Without either, it runs unscoped. Goblins a raid owner runs always join its scope.
- A scope starts with its first member and stops after its last member exits. Persistent scopes keep their storage and Docker data under =~/.cache/goblins=; temporary ones (=persistent = false=) delete it.
- Storage is a fresh directory managed by Goblins, mounted at =path=; it does not reuse what is already at that path on the host. Remove =rwDirs= entries for the same path when moving a cache into a scope.
- Every goblin that may join a scope must have the same online/offline network policy.
- =namespaces.pid.enable = false= stops members seeing each other's processes.
- =goblin status= inside a goblin shows its scope.

** Risks: scopes are trust groups, not isolation boundaries

Only put goblins you trust equally in one scope.

- Members can read and modify the scope's storage. With the shared PID namespace they can see each other's processes, read their command lines and environment through =/proc=, and signal them.
- Members share the scope's network, including published ports.
- With Docker, every member controls the same containers, images and volumes, and can reach other members' file grants through Docker. Read-only grants stay read-only but are readable by the whole group, and grants remain available until the engine stops, even after the granting goblin exits.
- Persistent images, build cache and volumes can keep source code and secrets. Leaving a persistent scope does not erase them, and there is no disk quota.
- Scopes are shared within one Goblins server; persistent scopes are locked so two servers cannot use one at once. Keep scope names distinct between unrelated trust groups.

Scopes are shared-kernel confinement, not VM isolation. See [[file:docs/USAGE.org::*Scopes (Linux, no VM)][the scope reference]] for the full rules.

* Docker

Goblins can give a scope its own rootless Docker engine. It does not use or need a Docker service on the host.

Enable Docker on the scope, then attach goblins to it either on request or at startup:

#+begin_src nix
mkGoblins {
  scopes.work = mkScope { docker.enable = true; };
  goblins = {
    # Attaches only when the goblin asks and you approve.
    claude = mkClaudeGoblin { scope = "work"; };
    # Attaches at startup, without a request.
    shell = mkGoblin { pkg = pkgs.fish; binName = "fish"; scope = "work"; docker.enable = true; };
  };
}
#+end_src

Inside a goblin of that scope:

#+begin_src sh
goblin enable-docker --reason "Run the integration test services"
docker compose up
#+end_src

The request appears in the TUI or Emacs like a package request. After approval the =docker= CLI is available and =DOCKER_HOST= points at the scope's engine. Codex and Claude Code goblins have a skill that tells them to do this.

What to expect:

- The engine starts when the first member attaches and stops after the last one leaves. All members of the scope share it.
- Builds, Compose and Testcontainers (including Ryuk) work.
- Ports published with =-p= are reachable from scope members on =localhost=, not from the host. =--network host= means the scope's network.
- Bind mounts work for the goblin's working directory and its granted directories, not for its private home or =/tmp=.
- Images, build cache and volumes live on disk under =~/.cache/goblins= (=$XDG_CACHE_HOME/goblins=), not on tmpfs. A temporary scope's Docker data is deleted when its engine stops; a persistent scope keeps it.
- Containers may write files owned by subordinate user IDs into writable directories.

See [[file:docs/USAGE.org::*Docker in a scope][Docker in a scope]] for all limits.

* Flake dev shells

Start a goblin inside a project flake's dev shell, like =nix develop=:

#+begin_src sh
goblins run shell --dev-shell .           # devShells.<system>.default
goblins run claude --dev-shell .#rust
#+end_src

The flake must be in the goblin's working directory and fully locked. Goblins evaluates it on the host in a restricted evaluator and mounts the result; the =shellHook= runs inside the sandbox only. Goblins a raid owner runs start in its dev shell.

When the flake changes, the goblin asks for the new version:

#+begin_src sh
goblin devshell diff                       # preview, no request
goblin devshell refresh --reason "added a formatter"
goblin devshell refresh --update nixpkgs   # update a lock input
goblin flake run '#fmt' -- --check         # run the flake's apps
#+end_src

The approval shows what changed: inputs, Nix files, packages, environment and what will be built. A goblin cannot change =flake.lock= behind your back; only locks you launched with or approved are trusted. See [[file:docs/USAGE.org::*Flake dev shells][the dev shell reference]].

* Raids

A /raid/ is a group of goblins that can message each other; goblins outside it are not reachable, apart from the host. The host invites goblins into a raid, or a goblin creates one and owns it. The owner can run new goblins into its raid with =goblin run CONFIG=, using only the configurations its =allowedRunTargets= lists, by default none, not even its own:

#+begin_src nix
goblins = {
  coordinator = mkCodexGoblin { allowedRunTargets = [ "coordinator" "reviewer" ]; };
  reviewer = mkClaudeGoblin { allowedRunTargets = [ ]; };  # runs nobody
};
#+end_src

A goblin the owner runs shares its working directory, scope and dev shell, but is not its child: it keeps running when the owner stops, and only the raid's owner can stop it. It can have access its owner lacks, if its configuration grants it, and packages approved for the owner before it ran are approved for it on request. It starts from the configuration the host last used, so a rebuild reaches new goblins after your next launch or a server restart.

#+begin_src sh
goblins raid invite review chief critic   # host: create raid 'review', owned by chief
goblin raid create crew                   # inside a goblin: create and own a raid
goblin run reviewer --name critic         # the owner runs a member
goblin raid members
goblin send critic --message "Please review the build."
#+end_src

When the owner leaves or stops, the raid pauses: its members keep running, but cannot message each other until you pick a new owner (=goblins raid set-owner=), or dissolve the raid (=goblins raid destroy=, with =--stop-members= to stop them too). The TUI and Emacs ask you when this happens. Codex and Claude Code goblins are woken when a message arrives. See [[file:docs/USAGE.org::*Raids][raids]] and [[file:docs/USAGE.org::*Manual inbox messaging][messaging]].

* Command line

=goblins --help= and =goblins help COMMAND= describe every command.

** On the host

#+begin_src sh
goblins server start                 # start the background server
goblins server status | logs | stop  # stop also stops every goblin
goblins tui                          # approvals; add --plain for a line-based UI

goblins configurations               # configured names, as JSON
goblins run CONFIG [--name NAME] [--detached] [--scope S] [--dev-shell FLAKE] [--raid R]
goblins list                         # running goblins and recent history
goblins history                      # conversations that can be resumed
goblins resume ID [--detached]       # resume one in a new goblin with the same environment

goblins attach NAME                  # reconnect a terminal
goblins detach NAME                  # detach it, leave the goblin running
goblins exec -t NAME                 # an extra shell inside the goblin
goblins exec NAME -- git status      # run a command inside it
goblins kill NAME                    # stop a goblin

goblins send NAME --message TEXT     # message a goblin
goblins raid invite|members|set-role|set-owner|destroy ...
goblins communications-log [--session NAME] [--follow]

goblins scope clear NAME [--dry-run] # delete scope storage and all its Docker data
goblins scope clear --all           # clear every stored scope, including retired ones
goblins gc [--dry-run]              # collect abandoned temporary stores and server resources
#+end_src

A goblin is addressed by its name, unique among running goblins, or its session ID. Names are lowercase letters, digits and hyphens. Without =--name=, the server picks a free fantasy goblin name.

=scope clear= requires the selected scopes to be unused. =gc= preserves persistent scopes, resume history and logs; it skips live temporary stores and running-server resources. Both leave host-mounted files and the Nix store alone. See [[file:docs/USAGE.org::*Clearing scopes and collecting abandoned data][Clearing scopes and collecting abandoned data]].

** Inside a goblin

Inside a goblin the command is =goblin=, so that a project's dev shell that ships the host =goblins= cannot shadow it:

#+begin_src sh
goblin status                         # name, configuration, scope, raid
goblin request-package NAME --reason TEXT
goblin enable-docker --reason TEXT
goblin devshell refresh | diff | restore-lock
goblin flake run [#APP] [-- ARGS]
goblin raid create NAME               # create a raid and own it
goblin run CONFIG --name NAME         # as owner: run a member into the raid
goblin list | stop NAME               # as owner: the members you can stop
goblin detach                         # detach this goblin's terminal
goblin send NAME --message TEXT       # message a raid member
goblin inbox status | next            # read messages
goblin editor open FILE               # open a file in your Emacs
#+end_src

=request-package= takes a nixpkgs attribute name, such as =cowsay= or =python3Packages.black=, from Goblins' pinned nixpkgs.

** Lifecycle

- Closing the TUI or a terminal leaves goblins running; =goblins attach= reconnects.
- A goblin stops when its program exits (=exit= or Ctrl-D in a shell). No other goblin stops with it.
- =goblins server stop= stops everything. Goblins do not survive a server restart or reboot, but =goblins resume= continues a goblin's conversation in a new goblin with the same environment: its current configuration, granted packages and Docker (see "Resuming conversations" in [[file:docs/USAGE.org][USAGE.org]]).
- =--state-dir DIR= runs a separate, isolated server; pass it to every command that should talk to that server.

** Shell completion

The Nix package installs completions for Fish, Bash and Zsh, including your configuration names and live goblin names. For a manual setup, use =goblins completions fish | source= or =source <(goblins completions bash)=.

* Emacs

The Emacs frontend is in [[file:emacs/][emacs/]]. It needs Emacs 28.1 or newer (29.1 for TRAMP), =magit-section= (part of Magit) and, for terminals, [[https://github.com/dakra/ghostel][Ghostel]] with its native module. Goblins installs no Emacs packages for you.

Add the directory to your load path, for example from the flake input in a Nix-managed Emacs configuration, or from a checkout:

#+begin_src emacs-lisp
(add-to-list 'load-path "/path/to/goblins/emacs")
(require 'goblins)
(goblins-ensure-server)    ; optional: start the server if it isn't running
(goblins-attention-mode)   ; optional: show pending requests in the mode line
#+end_src

If =goblins= is not on Emacs' =exec-path=, set =goblins-executable= to its absolute path.

Main commands:

| Command                                      | Purpose                                                              |
|----------------------------------------------+----------------------------------------------------------------------|
| =goblins-workspace=                            | Sidebar of running goblins, with each goblin's terminals and windows |
| =goblins-status=                               | Magit-style tree of goblins and requests; =a= / =d= accept or deny       |
| =goblins-run=                                  | Pick a configuration and start it in a Ghostel buffer                |
| =goblins-switch=                               | Jump to a running goblin                                             |
| =goblins-accept=, =goblins-deny=                 | Decide a pending request from anywhere                               |
| =goblins-shell=, =goblins-eshell=, =goblins-dired= | A shell, Eshell or Dired inside a goblin                             |
| =goblins-find-file=                            | Visit a file inside a goblin                                         |

=goblins-run= starts goblins in the current project's root and offers the project's =flake.nix= as dev shell.

Agents can't reach the clipboard from inside a goblin, so their own =Ctrl+V= image paste fails. In a goblin terminal, =C-c g v= pastes the clipboard's image instead: Emacs copies it into the goblin and pastes its path.

** Files inside goblins

Files and processes inside a goblin are reachable over TRAMP:

#+begin_example
C-x C-f /goblins:snikk:/tmp/diagram.svg
#+end_example

Dired, Eshell, compile, grep, Magit and Eglot work there, using the goblin's own packages.

To let goblins open files in your Emacs (for example =git commit= or an agent's "open in editor"), enable the editor on =mkGoblins=, and run an Emacs server with goblins.el loaded:

#+begin_src nix
mkGoblins {
  editor.emacs.enable = true;  # sets EDITOR and VISUAL in every goblin
  goblins = { ... };
}
#+end_src

#+begin_src emacs-lisp
(server-start)
#+end_src

Emacs asks before opening a goblin's files (=goblins-editor-approval=). Finish editing with =C-x #=.

See [[file:emacs/README.org][the Emacs guide]] for all keys, the workspace layout, Evil bindings and options.

* Security model and limitations

- Goblins is shared-kernel confinement built on Linux namespaces and seccomp, not a virtual machine. It has not been audited.
- Network access is open by default. Set =allowedDomains = []= for an offline goblin.
- The working directory and every =rw*= path you grant are your real files: the goblin can change or delete them. Use =goblins server start --workspace DIR= to give each top-level goblin a disposable copy at =/workspace= instead.
- Agent config directories are mounted writable, so agents can read your credentials there.
- An agent's own permission prompts are a second check inside the sandbox, not part of it. With =bypassPermissions=, the agent does whatever the sandbox allows without asking; without it, it asks as its own settings say, which your settings can also turn off. =goblin status= shows what the configuration requests, not the agent's effective mode.
- Package grants can only add packages from Goblins' pinned nixpkgs. They do not activate development setup hooks; use a dev shell for that.
- =allowNix= gives a goblin the whole host Nix store, read-only, and the host Nix daemon, as =allowNix= in agent-sandbox.nix does. It reaches no files directly, but the daemon acts for your user: if you are in Nix's =trusted-users=, which Nix documents as essentially equivalent to root, the goblin can import unsigned store paths and set daemon options, such as hooks the daemon runs as root, without any approval. The daemon's own downloads also ignore the goblin's network policy. Give =allowNix= only to goblins you would give that, or keep your user out of =trusted-users=.
- A host command (=hostCommands.enable=) runs as you, outside the sandbox, once you approve it, with your files, services, credentials and the server's environment. It runs whatever the files it reads say, such as scripts, build files and tests the goblin can change, also after you approved. Approve each one as you would let the goblin run anything as you.
- A raid owner runs only the configurations its =allowedRunTargets= lists, by default none; a goblin it runs has its own configuration's access, not the owner's. One with host commands or =allowNix= has them whatever its owner has.
- Goblins do not survive a server restart; a resumed one starts afresh apart from its packages, Docker and agent conversation. There are no live file or network grants yet, and no domain allowlist.
- At most 16 goblins run at once.
