#+date: 2026-09-13

For the next daemon milestone, this document supersedes the single-session,

Architecture, data flow and transport family below are settled. The
implementation contract below settles schemas, limits and transport details.

* Goals

- Run multiple simultaneous sandboxes in the first daemon milestone. A slow
  launch, unanswered approval or package build in one must not block control
  and permission handling for another.
- Move authoritative session, permission-request and approval state into a
  frontend-independent Rust daemon running as the ordinary host user.
- Keep sessions running when all frontends close, while the same daemon lives.
- Let a new frontend discover existing sessions, requests and approval outcomes
  from daemon state without the previous frontend's memory.
- Use established protocol machinery instead of a custom RPC envelope.
- Preserve live approved package grants, helper isolation and public Nix
  configuration semantics through the migration.
- Fix all three accepted review findings as protocol/frontend acceptance gates.

* Antigoals and scope boundaries

- No controller/daemon restart recovery: no sandbox survival across daemon
  death, checkpointing, durable recovery, restart reconciliation or replay into
  a replacement daemon. Daemon death ends helpers and sandboxes. Abrupt death
  may still leave host directories and GC roots for manual cleanup.
- Reconnecting a frontend to the /same live daemon/ is required. This is
  distinct from restart recovery.
- No terminal multiplexing, simultaneous terminal observers, input-ownership
  transfer, or explicit attach/detach management API in this milestone.
- Exact terminal screen, scrollback and frontend layout restoration are not
  required. Reliable output draining for a connected terminal is required.
- No project-management UI, general scheduling, automatic delegation,
  agent-controlled orchestration, remote hosts, web serving or rich UI work.
- No live file/network grants or revocation guarantee. File/network permission
  changes may require a fresh sandbox.
- No executable allowlisting boundary. Packages provision an environment;
  arbitrary agent code is expected. Store restriction protects unrelated store
  contents, and resource access remains the security boundary.

Future Herdr-like project/multiplexing state and operations remain open and may
be controlled by agents with appropriate authority. Do not turn this milestone's
small agent API or its provisional frontend/view-state distinction into a
permanent restriction on that future design. Detailed frontend architecture is
deferred; the approval-input safety contract is required now.

Emacs/Ghostel remains the preferred first editor frontend. Core runtime and
protocol must not require Emacs, Ghostel, a particular TUI or buffer identity.

* Ownership and data flow

| Component | State and responsibility |
|-----------+--------------------------|
| Daemon | Session IDs, selected launch configuration, lifecycle, request records, decisions, grant progress/results, GC roots, package provisioning records and PTY lifetime |
| Per-session helper | Retained namespace/filesystem handles, supervised sandbox process and execution/acknowledgement of narrow mount commands |
| Sandbox | Payload processes, memory, files and its actual mounted environment |
| Internal request client | RPC correlation ID, connection and returned outcome, including unknown outcome on interrupted communication |
| Frontend | Current presentation and interaction state; consumes daemon state and submits explicit control operations |

The daemon records what was authorized and confirmed. Kernel mounts determine
what is actually accessible; sending a helper command is not confirmation that
it succeeded. Helpers are stateful executors, not approval controllers. They
need no copies of frontend subscriptions or approval queues and no durable
recovery state.

#+begin_example
Host CLI/frontend -- sessions.start --------------------> Daemon
                                                          |
                                                creates helper + sandbox
                                                          |
Sandbox client -- per-session socket / permission ------> Daemon
Host frontend -- separate host socket / decision -------> Daemon
                                                          |
                                             private pipe / mount command
                                                          v
                                                   Session helper
                                                          |
                                               mount + acknowledgement
                                                          v
Sandbox client <------------ final permission result --- Daemon

Host CLI/frontend -- sessions.stop ---------------------> Daemon
                                                tears down this session
#+end_example

Sandbox permission requests go directly to the daemon, never through the
mount helper. Each sandbox gets its own request socket, mounted at the existing
=/run/goblins/request.sock= location. The daemon derives session identity from
that endpoint, not from a caller-supplied session ID or shared host UID.

The separate private host socket is for trusted host operations. The helper
retains private per-session pipes and accepts narrow canonical store-basename
mount commands. No public RPC exposes helper handles, caller-selected PIDs,
namespaces, destinations, mount flags, arbitrary Nix expressions or host Nix.
Trusted host =sessions.start= may select a manifest path; the sandbox API cannot.

Keep namespace operations in the small separate single-threaded Rust helper.
Keep blocking startup, Nix and helper waits off the daemon's control/event loop.
One worker per session is the straightforward extension of the current worker
design; exact thread/channel implementation is not a protocol commitment.
Sequential grants and one outstanding permission request per session are the
initial implementation direction; this must not become one global pending slot.

* Lifetime distinctions

- =sessions.start= is host-to-daemon launch control. The daemon creates the
  sandbox and helper. The host =goblins run NAME= command will use this path.
- =sessions.stop= is explicit host-to-daemon teardown, including owned work,
  helper, payload tree and session resource cleanup.
- Closing a frontend's control connection does not stop sessions, withdraw
  sandbox requests or forget accepted decisions. Its subscriptions end.
- Closing a sandbox request client's connection is not session stop. Before a
  decision, it withdraws that request and cancels its preview. After approval,
  the grant may still complete and that caller may have an unknown outcome.
- Natural payload exit ends the running workload. Payload exit, PTY EOF,
  terminal delivery completion and resource cleanup must not be collapsed into
  one event that prematurely drops output.
- Daemon death ends its sandboxes. A newly started daemon has a different
  instance identity; a frontend must not treat it as the previous live instance.

No detach operation is being added. The exact single-terminal connection
mechanics and output policy while no frontend consumes bytes remain to be
specified; they must honor session survival without claiming terminal replay.

* Protocol decision

Use *JSON-RPC 2.0 over pathname Unix stream sockets*, with *Content-Length
framing* for structured daemon communication. Use the same envelope and framing
on host and sandbox sockets, with separate dispatch/authorization surfaces.

#+begin_example
Content-Length: <UTF-8 body byte count>\r\n
\r\n
<JSON-RPC message>
#+end_example

The displayed =\r\n= denotes actual CRLF bytes. Terminal payload bytes use a
separate stream, not JSON-RPC notifications or JSON-encoded byte chunks. The
existing private helper command protocol remains separate for this milestone.

Prefer an existing JSON-RPC implementation where suitable. Library selection
must account for bounded parsing, streaming transport and the small internal
client's dependency boundary. Do not put host policy into shared protocol code.

JSON-RPC provides request/response correlation, result/error envelopes and
notifications. Goblins still specifies operation schemas, authorization,
application versioning, state transitions, subscriptions and resource limits.
=jsonrpc: "2.0"= is not the Goblins API version.

Content-Length framing matches existing editor RPC tooling, including Emacs's
=jsonrpc.el=, without imposing editor-specific application methods. gRPC and
D-Bus were considered; JSON-RPC was selected for readable structured operations,
multiple client implementations and minimal protocol machinery. MCP remains a
possible later thin agent adapter, not the sandbox transport or approval API.

References checked during planning:

- [[https://www.jsonrpc.org/specification][JSON-RPC 2.0 specification]]
- [[https://raw.githubusercontent.com/emacs-mirror/emacs/master/lisp/jsonrpc.el][Emacs JSON-RPC implementation and Content-Length framing]]
- [[https://man7.org/linux/man-pages/man7/unix.7.html][Unix-domain socket interfaces]]
- [[https://grpc.io/docs/what-is-grpc/core-concepts/][gRPC concepts]]
- [[https://dbus.freedesktop.org/doc/dbus-specification.html][D-Bus specification]]

* Initial method surface

** Common initialization

| Method | Contract |
|--------+----------|
| =initialize= | Negotiate Goblins API version; identify the daemon instance and report supported features and protocol limits appropriate to the caller |

Connect and disconnect are transport events, not dedicated RPC methods.
Initialization does not let a sandbox choose a host role or another session.

** Sandbox socket

| Method | Contract |
|--------+----------|
| =permissions.request= | Request permission for this sandbox; initially only =kind: "package"=; return one terminal result after decision/execution |

The initial sandbox surface is connect, request permission, disconnect. It has
no session list/start/stop, permission list/get/decide/cancel, subscriptions,
host paths or terminal-management operations. Additional authorized agent
operations can be designed in a later milestone.

Illustrative JSON body, excluding framing:

#+begin_src json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "permissions.request",
  "params": {
    "kind": "package",
    "package": "cowsay",
    "reason": "Run the example"
  }
}
#+end_src

The daemon creates its own immutable request/approval identities while the RPC
is pending. Host snapshots/events expose that record. This is not an immediate
submit-and-poll API on the sandbox side. The internal CLI succeeds only after
=ready=, reports denial/failure distinctly, and reports an unknown outcome for
missing/invalid/interrupted replies without automatic resubmission. Preserve
the existing success/denial-or-failure/unknown exit-code distinction (0/1/2).
Exact result schemas and application error codes remain to be specified.

** Trusted host socket

| Method | Contract |
|--------+----------|
| =sessions.list= | Discover session records, including starting/stopping sessions |
| =sessions.get= | Inspect one session's selected configuration summary, lifecycle and provisioned packages |
| =sessions.start= | Launch a named configuration from a trusted host manifest; return an ID and starting state once accepted |
| =sessions.stop= | Explicitly request teardown of the identified session; acceptance does not imply cleanup has finished |
| =permissions.list= | Inspect pending requests and retained decision/outcome records, filterable by session/state |
| =permissions.get= | Inspect an individual request, decision and execution outcome |
| =permissions.decide= | Approve/deny the exact pending session/request/approval identity |
| =state.subscribe= | Obtain an initial authoritative snapshot and subscribe to subsequent ordered changes |
| =state.unsubscribe= | End a subscription |

Daemon-to-host notification: =state.changed= carries the subscription identity,
sequence number and resource changes. Decisions must be RPC calls with replies,
not unacknowledged notifications. Only an accepted daemon response confirms a
decision; acceptance of approval is not confirmation of package readiness.

There is no =terminals.attach/detach=, observer, claim/release-input, project or
scheduling method set in this milestone. A generic jobs API is unnecessary for
the initial flow: session and permission records describe their ongoing work.

* Identities, transitions and synchronization

** Identity and duplicate handling

- A configuration name is a reusable label; a session ID identifies one launch.
- The daemon instance identifies one live runtime. Session/request/approval
  identities must not accidentally refer to objects in a replacement runtime.
- A JSON-RPC =id= correlates one exchange. It is not a session ID, approval
  capability or idempotency key. Reusing an agent's RPC ID cannot replace a
  pending approval or affect another client/session.
- =permissions.decide= targets immutable daemon-issued identities, not "the
  current request", a list position, package name or frontend selection.
- The daemon serializes competing decisions: only the first valid pending
  transition can authorize work. Repeated/stale/conflicting submissions never
  perform an additional grant or authorize a successor.
- Specify duplicate/retry behavior before implementing mutations, especially
  =sessions.start=. A lost reply is not permission for a client to repeat an
  uncertain launch or grant automatically. Exact idempotency keys, retention
  and duplicate response schemas remain open.

** Permission lifecycle

Conceptual transitions, not final wire enum spellings:

#+begin_example
validated request -> pending approval (advisory preview may run)
pending approval -> denied
pending approval -> withdrawn (sandbox request connection lost)
pending approval -> approved -> realizing -> mounting/publishing -> ready
approved execution -> failed
session stop -> cancel owned work / terminate session
#+end_example

Preview completion is not a decision and cannot grant access. Cancellation of
preview work must remain separate from session cancellation. Decisions and
disconnects are ordered by the daemon; after approval has been accepted,
disconnect does not imply revocation. A terminal outcome must remain distinct
from whether its reply was delivered to the sandbox client.

Retain the current failure boundary: realization/collision failure before
mounting leaves the sandbox usable; failure during mount preparation,
mounting or publication ends the affected session. Direct store paths may
already be visible before the profile switches. No rollback guarantee is made.

** Snapshots and events

=state.subscribe= establishes one snapshot at sequence N and delivers subsequent
changes after N without a gap. A new frontend can reconstruct daemon-owned
session/request/approval state without consulting a former frontend. List/get
remain available for one-off inspection; listing followed by an unrelated
subscription must not be the only way to initialize a live view.

Bound subscription buffering. A client that falls behind must be told to
resynchronize or disconnected so that it takes a fresh snapshot; do not
silently drop changes while presenting a continuous sequence. This requires no
durable event log or daemon-restart recovery. Exact snapshot sizing/pagination,
retention and sequencing schemas remain open.

* Framing, backpressure and authority invariants

- Enforce bounded headers, body lengths, JSON nesting, connections, pending
  work, diagnostics and outgoing queues. Bound per-session and daemon-wide
  resources so multiple sessions do not create unbounded work.
- Preserve the monotonic whole-frame deadline improvement. Header/body bytes
  cannot reset the deadline. The current three-second request-frame budget is
  the baseline; define initiation for initialization and later frames explicitly.
  Human approval/build waiting is separate and must not time out as framing.
- Validate malformed/duplicate fields, operation-specific unknown fields,
  parameter types and the existing bounded package grammar. Keep agent text as
  escaped data in approval views, never terminal instructions or approval input.
- Handle partial reads/writes and EOF throughout pending RPCs. Unexpected
  trailing input must be rejected or parsed under the bounded connection rules;
  unread bytes must never conceal a disconnect indefinitely.
- Keep host socket/session directories private and inaccessible through sandbox
  startup binds. All concurrent session-private paths must be protected, not
  only the requesting session's directory. Shared host UID is not sandbox scope.
- Helpers retain namespace-scoped authority, private handles and hardened
  read-only mounts. No main-daemon thread enters sandbox mount namespaces.
- Slow subscribers, terminal consumers and Nix operations must not block other
  sessions' control, approvals or shutdown. Backpressure behavior must be explicit.
- Cancellation stops/reaps owned Nix clients, not the host Nix daemon or shared
  build work. Existing filesystem/kernel cancellation limits still apply.

* Required review regressions

These gates are required even though JSON-RPC supplies standard envelopes.
The findings are accepted known defects in the current code, not fixed by this
document or invalidated by the previously passing test suite.

** P1: input queued for an old approval

Daemon decisions must name the immutable pending approval. The frontend must
also retain which request was actually presented for an interaction. Replacing
a request must not reassign queued keys, partial approval commands or mouse
interactions to the replacement. A token alone is insufficient: the existing
frontend already has tokens and still mislabels stale input.

Acceptance: display A, queue approval input, withdraw A and introduce B before
consuming that input. B remains unapproved. Test the actual approval frontend,
including the plain fallback if retained, and daemon rejection of withdrawn,
stale, duplicate and competing decisions. Reusing public RPC IDs cannot affect
the presented decision. Frontend implementation details can remain deferred
only until this required safety contract is implemented and tested.

** P2: terminal EOF drops buffered output

Represent payload exit/status, PTY EOF/EIO, buffered transport output and local
client output completion separately. An exit notification or accepted stop
response cannot cause the client to discard queued terminal bytes. Separate
control/terminal channels may deliver exit information before terminal draining
finishes. Normal completion drains buffered output; broken output delivery is
reported as interrupted/incomplete rather than successful completion.

Acceptance: the recorded slow-reader reproduction receives all 50,000 bytes and
the final marker before successful completion (the defect delivered only
16,384 bytes). A short command that exits immediately after writing also
delivers its output. Exercise partial writes/backpressure and EOF/EIO paths,
including exit information arriving before output drains. This requires neither
multiplexing nor detach/replay support.

** P2: trailing bytes hide request disconnect

Continue servicing the sandbox request connection while approval/preview is
pending. Do not rely on =MSG_PEEK= returning zero while leaving trailing input
unread. Reject unexpected input or consume it through bounded framing, and
recognize EOF/hangup even after an incomplete extra frame. Withdrawal cancels
preview work, removes the pending approval and releases the pending slot.

Acceptance: valid =permissions.request= frame + one extra byte + close withdraws
the undecided request and cancels/reaps its preview; a subsequent request can
proceed. Test fragmented input, silent/incomplete frames and slow drip input
against whole-frame deadlines. A race won by an already accepted decision is
reported consistently with the post-approval unknown-outcome rule.

* Nix and runtime compatibility

Preserve =mkGoblin=/=mkGoblins=, named presets/configurations, public flake
outputs, initial closures, literal entry arguments and literal =env= values.
Keep the restricted internal binary distinct from the host CLI. Neither the
daemon migration nor protocol selection introduces mandatory production Python.

Trusted host launches continue to supply a Nix-generated manifest path and
configuration name. Rebuilt configuration-only clients can start changed or
new definitions on the same daemon; running sessions retain their selected
configuration. Keep bounded regular-file manifest reads and launch work off the
control loop. Specify manifest/helper compatibility across builds explicitly
rather than silently imposing a fixed daemon configuration registry.

Preserve =mkSandbox= startup bind behavior, protected-path checks, exact
store-backed config targets, literal environment semantics and disposable
workspace snapshots. Bind variables currently expand in the =tui= process's
host environment; these are distinct from literal =mkGoblin.env= values. Daemon
launch/service packaging must explicitly define that environment rather than
silently changing variable sources. Per-launch workspace selection was not
settled in this discussion and is not implied by accepting manifest paths.

The daemon continues host-only pinned Nix resolution, closure rooting, helper
acknowledgements and profile publication. Each sandbox keeps its own live
grants and namespace-scoped helper; grants must not leak between sessions.

* Implementation phases and acceptance gates

These phases describe the authorized implementation. The preceding planning
commit contained no implementation. Intermediate refactors may be incremental, but a
single-active-session daemon is not the completed milestone.

** 1. Specify and test the protocol contract

Finalize schemas, initialization/version behavior, error codes, framing limits,
mutation duplicate handling and subscription ordering. Select suitable RPC
machinery. Define the three review reproductions as regression gates before
changing the corresponding paths.

Gate: protocol tests cover hostile framing, unsupported authority, duplicate
identities and stale decisions. Record terminal/approval integration scenarios
that cannot be established by protocol unit tests alone.

** 2. Extract daemon ownership and multiple sessions

Host the controller independently of =tui='s terminal. Replace the single
active-session slot with independently controlled sessions and workers/helpers.
Implement host lifecycle/inspection and the narrow sandbox permission flow.
Retain cancellation and mount isolation. An explicitly launched headless
command is the suggested first packaging step; service launch policy is open.

Gate: start at least two simultaneous sandboxes through the host API. A slow
build/preview/startup in A does not block status, request/decision handling or
stop in B. Grants and helper channels are isolated. Normal daemon shutdown
cleans all sessions; abrupt death kills their payloads without restart recovery.

** 3. State subscriptions and minimal frontend migration

Move approval presentation onto the host API and implement snapshot-plus-event
resynchronization. Keep the frontend independent from worker/session memory.
Implement and verify immutable displayed-input handling, not just RPC tokens.

Gate: close all frontends while multiple sessions and requests exist, then
connect a fresh client to the same daemon. It discovers sessions, pending
requests and retained decisions/results. Slow-client resync has no silent gap.
Competing frontends cannot double-decide a request. The P1 reproduction passes.
Rich Emacs/TUI and project-management work are not required by this phase.

** 4. Terminal completion and migration verification

Finish the separate terminal byte path and explicitly defined exit/drain
semantics without adding multiplexing or detach methods. Preserve ordinary
interactive terminal behavior. Complete both P2 regression gates.

Gate: all three review reproductions pass; existing live-grant, namespace,
configuration, startup-bind, literal-env, crash-teardown and responsiveness
coverage remains applicable and passes after adapting the interface. Run Rust
tests, formatting, Clippy, black-box tests and Nix/API/packaging checks. Record
actual results in =RESULTS.org= only after verification, and update current
usage/design documentation to describe the implemented behavior.

* Implementation contract (2026-09-13)

These choices settle the open details for API 1 before implementation.

- =goblins server start= explicitly starts the ordinary-user headless process in the background.
  =tui= becomes a host API approval frontend; quitting it leaves sessions
  running. No service installation or automatic restart. The daemon's
  inherited environment expands startup bind variables; =--workspace= on the
  daemon selects the snapshot source for every launch. Literal env/args remain
  literal. All session resources live below its protected private state directory,
  including future concurrent sessions, so an earlier bind cannot expose them.
- Use existing Serde/serde_json typed messages with a bounded Content-Length
  codec, without adding an async runtime or host dependencies to the inner client.
  A generic RPC server framework would still require this custom bounded Unix
  transport and authority dispatcher. JSON-RPC envelopes follow 2.0; no custom
  request/reply envelope is used. Reject batches. Notifications never mutate
  state and receive no reply; supported operations require an ID. IDs are
  strings of 1..64 ASCII identifier characters or nonnegative safe integers.
- =initialize {api:1}= is required once per connection. Its result contains
  =api=, =instance=, =role=, =features= and =limits=. Initialization cannot select
  a role. Sandbox connections permit one subsequent =permissions.request=
  with ={kind:"package",package,reason}= or ={kind:"docker",reason}=, then one
  terminal response and close. The =docker-enable= feature advertises the latter.
  The =docker-scopes= feature adds optional =scope:string= or =anonymous:true=
  (mutually exclusive). Names must be allowed by the session configuration;
  absent options select the current/default scope. Anonymous is always allowed.
  Docker requests accept no nonempty package or caller-selected runtime options;
  they use the same explicit host approval and withdrawal rules. They never
  inherit ancestor package approval. Already-enabled sessions selecting the
  same scope return ready without approval; explicit anonymous creates a fresh
  scope. Children inherit the parent's live scope and activation without a new
  Docker request, including anonymous scopes. =docker_enabled= is separate from
  package grant state.
  Host connections permit sequential calls and ordered notifications; at most
  4096 calls per connection. No automatic retry of uncertain mutations.
- Headers are ASCII, at most 256 bytes, one case-insensitive Content-Length and
  optionally Content-Type (UTF-8 JSON); no duplicate/other headers. Host input
  bodies are at most 16 KiB, sandbox input 4096 bytes, output 1 MiB, nesting 32.
  Duplicate JSON keys at any depth and unknown operation fields are rejected.
  A whole-frame three-second deadline starts on accept for initialization,
  on completion of sandbox initialization for its request, and on the first
  byte for later idle host frames. Pending human/build waits have no deadline.
  Any byte after a sandbox permission frame terminates that connection;
  undecided work is withdrawn and its preview cancelled. No MSG_PEEK.
- Standard errors: -32700 parse, -32600 envelope, -32601 unavailable method,
  -32602 params. Application errors: -32001 initialization required,
  -32002 incompatible version, -32004 absent/evicted record, -32009 stale or
  conflicting operation, -32010 resource limit. Permission results contain
  =status= (=ready=, =denied=, =error=), =request=, and optional =message=.
  Only ready is client exit 0; denial/failure is 1; invalid/missing/interrupted
  replies are unknown outcome, exit 2, without retry.
- IDs contain a random 128-bit daemon instance prefix and monotonic counters.
  =sessions.start {key,configuration,name,agent_name?,cwd?,rows,cols}= requires an absolute
  trusted manifest path and a caller-generated identifier =key=. Optional =cwd=
  is an absolute host directory, bound read/write at the same path and used as
  the shell working directory. The CLI supplies it for each run. Omitting it
  retains the legacy =/workspace= behavior; an explicit daemon =--workspace=
  overrides it with a disposable snapshot. Repeating
  an identical key/params returns the original session ID; changed params
  conflict. Keep at most 4096 launch keys for the daemon lifetime, then reject
  new launches; never silently reuse an expired key. Manifests carry
  =api:1,helper_api:4=; configuration-only rebuilds may select new helper paths
  implementing private helper API 4 (shared scope/store, bind and forwarding
  entry points and the unchanged
  =READY2= shell startup acknowledgement).
  Incompatible manifests/helpers fail that launch.
- =sessions.get/stop {session}= accept an exact ID or live agent name; =sessions.list {}=; =permissions.get {request}=;
  =permissions.list {session?,state?}=; =permissions.decide
  {session,request,approval,approved}=. Only the first pending decision wins.
  Stop by ID is idempotent while the record exists. Names address only live workers. A small =sessions.resize
  {session,rows,cols}= operation preserves terminal resizing; it conveys no
  attachment or namespace authority. Dimensions are 1..1000.
- Limits: 16 live sessions, 128 retained session records, 256 permission records,
  128 initial package entries and 64 provisioned package names per session,
  32 host connections, 8 sandbox
  connections per session, one pending request/grant per session. Evict oldest
  terminal records only, also pruning terminal history to keep a snapshot below
  900 KiB; exposed diagnostics are capped at 512 characters.
  Get on an evicted identity returns -32004. IDs never
  repeat. Launch-key lookup still reports the original ID after record eviction.
- =state.subscribe {}= returns ={subscription,sequence,snapshot}= atomically.
  Subsequent =state.changed= notifications contain the same subscription,
  increasing global sequence and a complete replacement =snapshot= of bounded
  session/permission records. This deliberately simple replacement schema
  includes evictions without a durable log or pagination. One subscription per
  connection; =state.unsubscribe {subscription}= ends it. Queued output is
  bounded to 2 MiB per host connection; overflow disconnects the subscriber,
  which must initialize and subscribe afresh. No silent notification loss.
- Start returns ={session,agent_name,state:"starting",terminal}=, where =terminal= is a
  private per-session Unix STREAM path accepting one terminal consumer at a time.
  Each connection first receives a Content-Length framed JSON-RPC response with
  id 0: ={attached:true}= on success, or an error on rejection. Raw bidirectional
  terminal bytes follow the success frame. Host initialization advertises
  =terminal-reattach=; clients and daemon must both support this handshake.
  The daemon owns the master and pumps bounded 64 KiB buffers. Before the first
  consumer, and while attached, output backpressures the payload. While detached
  or disconnected, the daemon continues draining and retains a bounded output
  tail; older bytes may be discarded. There is no full screen or durable replay.
  A sandbox may call =sessions.detach {}= on its own request endpoint (advertised
  as =terminal-detach=), with no target parameter or host authority. This returns
  ={accepted:true}= and half-closes the terminal output. The departing client
  drains local stdout, observes =terminal_detached=true= and exits 0. Its read
  half stays reserved until the client closes, preserving the detach outcome
  against a concurrent attachment. Input from a detaching client is discarded.
  =terminal_attached= and =terminal_detached= are included in session snapshots.
  On the next accepted attachment, detached/interrupted state resets. An
  unexpected consumer disconnect marks interrupted delivery but permits reattach.
  Process exit/status, PTY EOF and terminal-stream completion remain separate;
  normal completion waits for EOF and local output drain before checking the
  retained exit/delivery result. Daemon loss and failed output delivery are errors.
  Host CLI =attach NAME= resolves a live name once to its immutable session ID;
  =attach ID --instance INSTANCE= retains the editor's exact identity checks.
  Host =kill NAME= uses =sessions.stop=, as does the retained =stop= command.
  Host =detach NAME= calls =sessions.detach {session:NAME}=,
  accepting a live name or immutable ID and using the same detach behavior.
  Unknown sessions return -32004; unattached terminals return -32009. Sandbox
  detach still takes no parameters and cannot select another session.
  This extension supersedes the earlier milestone's single-consumer/no-detach
  scope statements above.
- User-requested frontend revision: fullscreen keeps the information popup,
  Yes/No buttons, mouse and =y=/=n= shortcuts. Tab switches sandbox/request
  focus; Up/Down selects entries. The popup reserves bottom rows. Escape closes
  it without cancelling the request; accepted decisions close it automatically.
  The list stays visible; navigation or Enter reopens details. Selection
  stays bound to its immutable request after withdrawal/completion. Input
  batches target the last rendered identity; selecting another row cannot
  activate it before presentation. Mouse release must match the press identity.
  Bracketed paste is ignored. The plain fallback retains complete
  =approve APPROVAL=/=deny APPROVAL= commands with immutable token text.

Integration gates include suspending the actual frontend after A is displayed,
queueing its approval keys or plain complete/partial command, withdrawing A and adding B,
then resuming it; B must remain pending. Terminal tests include 50,000 bytes
plus final marker through a slow local PTY reader, immediate short output and
exit status preceding stream drain. Protocol tests alone do not establish these.

** API 1 record and snapshot schemas

Objects below have the listed fields; clients should tolerate additive result fields. Optional values are JSON null,
not omitted, except where JSON-RPC itself specifies optional envelope fields.
Input parameter objects reject unknown fields. Lists/get return the record or
array directly; stop/resize/unsubscribe return ={accepted:true}=. Decide returns
={accepted:true,request,approved}=. A duplicate start returns its original
acceptance object; use get to inspect its current lifecycle.

| Record | Fields |
|--------+--------|
| Snapshot | =instance= (string), =sessions= (Session array), =permissions= (Permission array) |
| Session | =id,agent_name,name,configuration,state,terminal= (strings); =identity= (Identity or null); =initial_packages,packages= (string arrays); =pty_eof,terminal_complete,terminal_interrupted,terminal_attached,terminal_detached= (booleans); =exit_code= (integer or null); =detail,stop_reason= (strings or null) |
| Identity | =pid,helper_userns,mount_owner,source_mountns,mountns= (integers; trusted host inspection only) |
| Permission | =id,session,agent_name,approval,kind,package,reason,state= (strings); =approved= (boolean or null); =preview= (Preview or null); =message= (string or null) |
| Preview | ={in_store:boolean,download:string-or-null,build_required:boolean}=, ={error:string}=, or ={description:string}= for Docker |

Session records (host and sandbox views) also include =docker_enabled:boolean=
and =docker_scope:string-or-null= (null means anonymous). Permission records
include =scope:string-or-null= and =anonymous:boolean=.
For =kind:"docker"=, =package= is a display label for the engine/scope, not a Nix
attribute or an entry in the session's =packages= list.

Session states are =starting,running,stopping,stopped,failed=. The =stopped=
notification follows worker cleanup, while terminal buffering may still be
draining. A failed launch has no payload exit code. A normal payload exit has
its exit code; signal exits use =128 + signal=. Explicit cancellation can leave
an unknown/null payload exit code. PTY/stream end and terminal interruption are
separate from those workload states.

Permission states are =pending,realizing,mounting,publishing,ready,denied,
withdrawn,failed,cancelled=. =approved= records accepted authorization separately
from execution. Preview errors never grant or cancel a session. Approved caller
disconnect does not revoke authorization; readiness can still be retained even
when no caller receives its reply. Snapshot/event schemas contain daemon-issued
identities, never an agent's RPC ID as approval authority.

The helper's versioned =READY2= acknowledgement includes the five Identity
integers. Mount acknowledgements remain =OK= after one canonical store basename.
The helper polls its private pipe and child status, exiting with the workload's
status. No daemon thread performs namespace operations.

Helper API 2 passes an explicit startup-source descriptor list before the
Bubblewrap executable argument. The daemon opens each declared bind source,
validates the opened object's resolved location and kind, and keeps that handle
through both exec boundaries. Bubblewrap mounts with =--bind-fd=/=--ro-bind-fd=
and closes the handles before payload execution. Helpers implementing API 1
are incompatible with this launcher contract and must be rebuilt. Goblins
JSON-RPC remains API 1.

** Agent naming extension (API 1)

The daemon owns per-launch names; Nix =mkGoblin/mkGoblins= configuration names
retain their existing meaning and public API. =sessions.start.name= and
=Session.name= remain the reusable configuration key; =configuration= remains
the manifest path. Optional =sessions.start.agent_name= is a requested agent
name, with omission/null selecting automatic allocation. Start acceptance,
Session and Permission records expose the allocated =agent_name= string. Host
=initialize.features= includes =agent-names=; the sandbox method surface is
unchanged. Existing API launch requests remain valid.

Explicit names match =[a-z][a-z0-9-]{0,31}=. Invalid names return -32602;
explicit-name collisions return -32009 with an already-in-use message.
Automatic allocation filters the checked-in =crates/controller/src/goblin-names.txt=
to available entries and picks one uniformly at random. Its 128 unique names
provide variety beyond the unchanged 16-worker limit. OS randomness from
=/dev/urandom= is sampled with rejection to avoid modulo bias, bounded at eight
64-bit samples. Entropy read/open failures or repeated rejected samples return
-32010 without accepting a launch. Exhaustion returns -32010 with an
automatic-pool-exhausted message, with no probing occupied names or suffixing.
General resource bounds also continue to apply.

Allocation, record insertion and launch-key retention execute in one daemon
control-loop operation. A name is reserved while its worker is present,
including startup, stopping and final lifecycle messages awaiting complete
worker cleanup. Release follows the disconnected/drained worker result channel
and confirmed worker exit; PTY output may continue draining afterward. Historical
records retain the original name and ID until evicted. Duplicate names in history
are expected; IDs never repeat. Names are scoped to one daemon lifetime.

Launch-key lookup precedes allocation and capacity checks. An identical retry
returns its original acceptance (ID/name/terminal/starting state), even after
completion, eviction or name reuse. Requested names are part of parameter
comparison. Omission and null compare equal; changing an automatic request to an
explicit allocated name conflicts. Rejected launches do not reserve names or keys.

Host =sessions.get/stop.session= accepts an exact immutable ID or a live agent
name. IDs take precedence; generated IDs are longer than the name grammar
allows, so the namespaces cannot collide. Name lookup excludes historical
records and is serialized with stop. An absent live name returns -32004. Names
are convenience selectors, never approval identities: =permissions.decide=,
permission filters and resize still use IDs. The sandbox's session is always
derived from its endpoint. Permission =agent_name= is copied from that session
at request creation, so permission details/events remain intelligible after
session eviction or reuse without changing immutable decision identities.

The CLI accepts =run CONFIG --name NAME=; omission uses
the daemon allocator. List/status, fullscreen session/request views and plain
permission details display names while session inspection retains configuration
identity. Renaming, projects, scheduling, multiplexing and restart recovery are
outside this extension.

** Server management and CLI revision

The public daemon command is =goblins server start/stop/status/logs=. The old
=daemon= and =shell= commands are removed; =goblins run shell= automatically
allocates a name unless =--name= is supplied. =tui= remains the approval UI.
Clap supplies the command tree, per-command help and argument validation;
clap_complete generates completion scripts, including the selected manifest's
configuration keys. Nix packages install Bash/Fish/Zsh scripts. Neither help nor
completion generation requires a server.

=server start= spawns this executable with =server start --foreground= in a new
POSIX session, stdin closed and stdout/stderr appended to private
=STATE/server.log=. It inherits environment/cwd; no supervisor, service unit,
PID file, automatic restart or recovery is introduced. Start waits for host API
initialization before succeeding, up to ten seconds. A failed/interrupted start
reaps only its own spawned child. Existing servers are left unchanged.

Host API 1 adds =server.status {}= returning
={instance,state,sessions}=, with =state= running/stopping and =sessions= the
live worker count. =server.stop {}= returns ={accepted:true}=, then closes the
connection and gracefully tears down every agent and the daemon. Host
initialization advertises =server-control=. These methods are unavailable on
sandbox endpoints. The daemon flushes the stop acceptance before teardown,
allowing at most one second for a stalled response queue; a missing reply is
still an unknown outcome. Once stop is accepted, subsequent host operations
other than server status/stop are rejected with -32009.

The CLI waits for the daemon lock to be released after stop acceptance, bounded
at fifteen seconds. Timeout/interruption reports incomplete cleanup without
forcing any PID. The daemon lock remains held through worker/resource cleanup.
A separate =server-control.lock= serializes background start/stop clients;
concurrent callers may receive a lock-held error. Foreground start retains the
same exclusive daemon lock. =server status= does not equate a stale socket with
a running server: it initializes on the host endpoint and reports errors from
unresponsive/incompatible peers. Status/logs do not create missing state.

=server logs= prints captured background stdout/stderr verbatim once. Log writes
append across starts; symlink/special-file/nonprivate log paths are refused.
Foreground output goes to its caller. No follow, rotation or sandbox-output
aggregation is implemented. See [[file:../../USAGE.org::*Server commands, help and completion][usage and completion setup]].

* Ownership tree and sandbox lifecycle control (2026-09-19)

This section extends API 1 and supersedes the earlier host-only lifecycle and
daemon-wide name-allocation rules.

- The host is the root, represented by a null =SessionRecord.parent=. Each
  sandbox record has an immutable parent session ID and a =path= assembled from
  sibling-scoped agent names. Ownership never relies on names. Records with
  retained children cannot be evicted before their children.
- Host =sessions.start= adds optional =parent= and =detached= fields. Omitting
  =parent= creates a root child. A selected parent must be running. Children use
  its loaded configuration and opened filesystem grants, including its shared
  workspace, regardless of which host manifest the caller supplies. The
  configuration key must match the parent's key.
- Sandbox =initialize= advertises =subtree-control= and reports only the caller's
  configuration key in =configuration=. Its socket selects its identity.
  Sandbox =sessions.start {key,name,agent_name?,parent?,detached?}= creates a child, returning
  =session=, =agent_name=, relative =path= and starting =state=. The default parent
  (also =.=) is the caller; explicit parents must be running descendants. Host
  launch fields (manifest, cwd, dimensions, etc.) are rejected on this endpoint.
  Sandbox launches default to attached delivery (=detached=false=). Retry keys are scoped by caller ID;
  host retry keys have a separate scope.
- Sandbox =sessions.list {}= and =sessions.get {session}= expose only descendants.
  Their records contain =id=, =agent_name=, =parent= (null for direct children),
  relative =path=, configuration key =name=, =state=, =initial_packages=,
  =packages=, =exit_code=, =stop_reason= and =terminal_attached/terminal_detached/terminal_complete/terminal_interrupted=. They omit host filesystem paths, process identities,
  terminal endpoints, and host diagnostics. Outside-scope IDs and names return
  the same absent-record fault as unknown IDs and names.
- Host and sandbox =sessions.stop {session,kill_children?}= reject an operation
  with live descendants unless =kill_children=true=. The check and subtree
  cancellation occur in one event-loop operation. Sandbox targets must be
  descendants, excluding the caller itself. CLI =kill= and =stop= expose
  =--kill-children=. A normal exit or failure always cancels descendants; pidfds
  let the controller observe exit while the worker is blocked on Nix work.
- Full tree paths and exact IDs identify descendants from the host. Sandbox paths
  are relative to the caller. A bare name resolves a direct child first, then a
  unique descendant; ambiguous names require a path or ID. Completions use only
  the caller's visible records, and parent completion includes running nodes.
- Host approval remains authoritative. Successful grants retain the exact store
  output privately. A request covered by the caller or an ancestor's successful
  grant reuses that output automatically. Otherwise the request goes to the host.
  Descendants receive no extra mounts until they request the package, and grants
  never flow upward or sideways. Pending descendant requests are reconsidered
  after ancestor grants complete. Initial-package auto-approval compares resolved
  store outputs, not display names. The inheritance decision lives in
  =Controller::inherits_package= so its policy can be changed independently.
- Host and sandbox =run= attach by default. =run --detatched= (alias =--detached=)
  returns the accepted launch JSON without attaching. Initially detached
  terminals drain into a bounded tail without waiting for a first attachment.
- Sandbox =sessions.attach {session}= resolves only descendants and upgrades the
  authenticated request connection: its framed result ={attached:true}= precedes
  raw terminal bytes. No host terminal path is exposed. Pipelined RPC input is
  rejected during upgrade. The terminal permits one consumer, shared with host
  attachments. =sessions.resize {session,rows,cols}= is also descendant-scoped.
  Sandbox =initialize= advertises =subtree-terminal= and =sandbox-status=.
- Sandbox =sessions.status {}= returns the endpoint owner's =id=, =agent_name=,
  configuration key =name= and =state=. It accepts no target. CLI =status= prints
  this identity. The existing sandbox self-detach operation remains self-scoped.
  Server control, host approvals and subscriptions remain unavailable.

Children retain host-owned shared mount capabilities rather than reopening paths.
In particular a renamed/replaced workspace source does not widen their access.
Workspace resource ownership is retained until the last dependent session stops;
child startup does not copy a parent's snapshot or inherit its package mounts.

** Stop attribution

=stop_reason= is a daemon-authored explanation, null for natural payload exit.
Explicit stops identify the host or the requesting goblin's name and immutable
session ID. Descendants stopped by that request retain the same attribution;
automatic cleanup after an owner exits identifies that owner. Repeated stops
preserve the first cause. This field is exposed on both host and sandbox
session records without exposing host diagnostics. Once terminal output is
complete, an attached client with no payload exit code reports this reason
before falling back to =detail= or an unknown exit status.
