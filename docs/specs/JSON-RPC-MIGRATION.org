The user wants the full JSON-RPC contract, implemented in vertical chunks. Each chunk follows this order: define its JSON-RPC specification, generate types where possible, migrate its producers and consumers, then validate. Do not implement all schemas first, all generators next and all consumers last.

This plan replaces the implementation schedule in [[file:API-SCHEMA.org][API-SCHEMA.org]] and expands its inventory to private JSON-RPC. That earlier draft remains design background. [[file:ARCHITECTURE-REVIEW.org][The architecture review]] explains the motivation; [[file:../API.org][API.org]] and the implementation describe current behavior. * Scope and invariants

All repository-owned existing JSON-RPC surfaces are in scope: host, sandbox, attachment, daemon/supervisor, scope control/member and Docker guardian. Full coverage includes requests, results, errors, notifications, nested records, method availability, direction and protocol sequencing; records alone do not complete a surface.

The non-JSON-RPC interfaces discovered during the inventory are recorded below with their current definitions and a disposition. Converting init, helper lines, shared files or arbitrary CLI output to JSON-RPC is not implicitly authorized by a type migration; a conversion needs an explicit protocol decision and its own four-step chunk. Raw terminal bytes, stdio, signals and locks remain their existing protocols. External protocols are consumed rather than redefined here.

Public wire behavior stays compatible: names, fields, error codes, defaulting, absence versus null, unknown-field policy, limits, feature negotiation, host/sandbox visibility and error precedence. Record any disagreement between code and documentation during step 1; decide it before migration rather than silently treating generated behavior as correct. Report behavior changes separately for user decision.

Private channels retain their same-build compatibility policy and their existing wire format in this migration. Neither generated metadata nor a shared Rust type may weaken descriptor validation, cleanup ownership, bounds, cancellation, fairness or adoption barriers. A private wire-format simplification is a separate change.

Wire DTOs describe data, not authority. Keep runtime ownership, validation and controller lifecycle operations handwritten. Moving record definitions must not create a dependency from =libs/api= back to =libs/runtime= or the daemon; introduce descriptor-free public projections for runtime-owned nested types. State enums must not become permission to set state without its existing lifecycle consequences; lifecycle redesign is separate work.

* Contract format and generation

Carry forward the schema-first direction of the earlier proposal: JSON OpenRPC endpoint descriptions referring to shared JSON Schema definitions. Prove generator suitability in C01 rather than assuming every schema feature maps faithfully to Rust. =typify= is the initial Rust generator candidate, not an excuse to change accepted input.

- Public documents: =libs/api/schema/host.openrpc.json=, =sandbox.openrpc.json= and =attach.openrpc.json=, with common record/error definitions. A method is identified by endpoint and name, not by its name alone.
- Private documents: separate supervisor, scope-control, scope-member and guardian descriptions alongside their owning runtime contracts. Keep descriptor schemas and ownership annotations private; do not expose them through the public API crate.
- Every message records its direction and request/notification role. Notifications in either direction have a separate =x-notifications= section with explicit sender, receiver and legal connection state; they never enter a callable-method allowlist. This includes the host client's =exec.signal= during an active exec as well as daemon-to-client updates. Attach's fixed-ID completion reply needs an explicit exchange description rather than a fictitious callable method.
- Describe required/nullable fields, omission, defaults, unknown fields, unions, integer ranges, string/collection limits, byte limits and method-specific errors. Defaults in a schema do not themselves implement runtime defaulting. Common protocol errors apply before a method has been identified; they cannot be validated solely against a method's error list.
- Document state/order constraints, actor/authority derivation, path visibility, request cancellation, delayed completion, retries/idempotency, sequence gaps and resource release in descriptions or linked prose. Do not claim JSON Schema enforces these properties.
- Generate Rust DTOs, endpoint method/notification identities and a reference from the covered descriptions. Build Rust into =OUT_DIR= using pinned, offline-available inputs. Keep method-specific request/result association in the client API so a caller cannot accidentally pair one method with another method's DTO.
- For constraints the generator cannot preserve, keep a named handwritten validator or wrapper, state the exception in a registry and prove equivalence with wire cases. Do not replace closed variants with =Value= merely to make generation succeed. Genuine opaque data, such as flake lock contents, stays JSON and is explicitly identified.
- Rust handlers, host/sandbox CLIs, TUI and both adapters migrate in the chunk owning the method. The sandbox gate uses the same parameter contracts while retaining its policy checks and refusal order. Domain types may differ from wire DTOs through explicit conversions.
- Python test clients validate covered responses and notifications against the schema. Emacs, shell and TypeScript consumers receive contract fixtures and boundary checks; generated TypeScript DTOs are added where useful, with runtime validation where data enters. No Elisp or shell generator is assumed, and static TypeScript types alone do not validate JSON.
- Keep =API.org= updated in every chunk under the existing repository rule. Generate a separate reference for covered surfaces, linking it from =API.org= without removing the reference for unmigrated surfaces. If the documentation ownership rule changes, change =AGENTS.md= explicitly in that chunk.

* Execution and completion rules

Each numbered chunk below is one logical migration, with this required sequence:

1. *Spec*: reconcile the implementation and =API.org=, write the covered endpoint entries and referenced records, define positive/negative wire examples and behavioral assertions.
2. *Generate*: generate the chunk's DTOs and method identities; record unsupported constraints and their handwritten enforcement. Step 1 may define record dependencies needed by that chunk without pre-migrating unrelated methods.
3. *Migrate*: switch all in-repository producers, Rust consumers and parameter gates for the covered methods, and update non-Rust boundary checks/fixtures. Remove superseded definitions and manual field access for covered DTOs. Explicit conversions may bridge generated records into an unmigrated snapshot or domain model; label and retire them in the owning later chunk.
4. *Validate*: check schemas/generation/reference freshness and malformed/valid wire behavior, run the applicable feature tasks, and review the uncommitted diff. Fix findings before committing. Run the merge gate on the final candidate before merge.

Do not merge a spec-only or unused-types-only implementation phase as the completion of a chunk. A chunk can have intermediate local changes, but its reviewable result must exercise the generated contract in production. If a listed chunk is too large, split it by method family before implementation; each resulting chunk repeats all four steps.

Until the public migration is finished, contract checks have an explicit coverage registry: every callable method, notification in either direction and protocol-specific exchange is either covered or assigned to a remaining chunk. Include paths outside ordinary dispatch, such as active-exec input and attach handshakes. Separately register deliberate refusal/behavior entries, such as sandbox =sessions.attach=, and wildcard/unknown-method handling; recognized names that only refuse a call never enter the generated callable allowlist. Unknown covered notifications/results fail validation; uncovered surfaces remain visible as pending rather than pretending to be checked. At C15, remove the transitional exemptions and require exact coverage of available methods, notifications, special exchanges and refusal behavior. Keep deliberately malformed-frame fixtures independent of normal parameter validation.

Introduce nested records in their first consuming chunk. For example, C02 owns the public session projection, C05 terminal records, C09 permission records, C11 raids and C12 messages. Preserve adapters to legacy snapshot records until C15 rather than generating the whole API up front.

The order below is a default serial implementation order. Dependencies name the prerequisites when work is split; they do not authorize concurrent test runners. C16-C19 follow the public contract so relayed payloads can reuse it.
