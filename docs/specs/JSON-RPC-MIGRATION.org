#+title: JSON-RPC contracts: implementation and remaining boundaries
#+startup: showall

* Current scope

The migration specifies the existing repository-owned JSON-RPC surfaces and uses generated Rust wire types and typed method/notification associations at their process boundaries. It covers host and sandbox calls, attachment handshakes, state notifications, daemon/supervisor control and operational messages, scope control/member messages and Docker guardian retention. Runtime policy, transport and resource ownership remain handwritten. This document records the current design and follow-up inventory; the original chunk plan and detailed validation diary remain in Git history.

Generated Elisp provides lazy record views and accessors, not static type checking or eager whole-record validation.

* Boundary coverage

| Boundary | Contract role |
|----------+---------------|
| Host and sandbox endpoints | Endpoint-specific requests/results, errors, parameter forms, notifications, visibility and method availability |
| Terminal attachment | Hello/waiting notifications and fixed-ID completion replies; raw PTY bytes begin only after successful completion |
| State subscriptions | Subscribe/unsubscribe results, snapshots, directional updates and compatible client projections |
| Daemon/supervisor | Bootstrap, maintenance, adoption, lifecycle, launch/handoff, processes, terminals, approvals/devshell, host jobs, sandbox relay and logging |
| Scope control/member | Setup, membership, join, storage, registration, bounded Docker transactions, leave and error replies |
| Scope/Docker guardian | Retain/Retained and lease metadata; bootstrap descriptor ownership and cleanup remain handwritten |

* Invariants and deliberate choices

Wire DTOs describe data, not authority. Do not introduce a dependency from =libs/api= back to =libs/runtime= or the daemon. Domain records may remain separate where they own methods, policy or resources; explicit conversions connect them to generated wire records.

Private same-build channels retain their existing envelopes, field names, absence/null behavior, descriptor ordering, validation order, budgets, cancellation, adoption and cleanup ownership. Opaque relayed application JSON remains opaque on the wire so descriptor-looking user data cannot acquire capabilities. Local worker queues remain Rust enums rather than becoming RPC endpoints.

Canonical producer shapes and compatible reader profiles serve different purposes. Preserve intentional differences explicitly. The user accepted implemented diagnostic wording and stricter client reading rather than requiring restoration of every historical tolerance merely to call the migration a pure refactor. Further observable behavior changes still need to be identified and explained.

Public request handlers retain endpoint visibility, accepted parameter forms, defaults, error codes and policy gates. A type must not grant authority to set lifecycle state or bypass host/sandbox checks. Semantic limits and fieldwise validation remain handwritten where generation cannot preserve them faithfully; record those exceptions rather than claiming JSON Schema enforces process behavior.

For future protocol changes, define the JSON-RPC contract first, generate types where possible, migrate producers/consumers, then validate. Prefer small independent wire examples and focused regressions over exhaustive wrong-type fixture matrices or duplicate schema checkers. Never generate expected test results from the schema under test.

* Other process contracts

These interfaces were inventoried but are not existing repository-owned JSON-RPC endpoints. Converting one requires a separate protocol decision; its presence here does not authorize a conversion.

| Boundary | Current definition | Proposed disposition |
|----------+--------------------+----------------------|
| Supervisor/init | Serde =Command= / =Event= in =libs/api/src/init.rs=, seqpacket JSON and SCM_RIGHTS; no JSON-RPC envelope | Retain same-build init protocol; decide separately whether a generated schema for its existing messages or JSON-RPC conversion is useful. |
| Supervisor/mount helper | Arguments/inherited FDs; matching parsers for =MOUNTNS= / =RELEASE= / =READY2=, grant lines, =OK= / =ERR= and EOF | Candidate follow-up for a structured protocol; specify bootstrap and restricted helper dependencies before choosing conversion. |
| Host-job helper | Arguments/environment, lifetime-pipe EOF, output log; helper-local manual =status.json= writer and runtime =HostOutcome= reader | Candidate shared/generated file contract; preserve atomic completion and cleanup-before-result, rather than assuming it needs a request server. |
| Namespace keeper, Docker startup/mount injection and cleanup helpers | Arguments/FDs, readiness byte/PID/file handshakes, release gates, exit status and EOF | Document as bootstrap/lifetime protocols; convert structured metadata only after an explicit decision. |
| Claude hooks/monitor/mod | Rust =Hook= / =Ledger= subsets, JSON stdin/stdout/status, wakeup lines, shell PID/file conventions and TS parsing | Daemon RPC contracts cover messages; provider input, local ledger/status and monitor protocols remain separate contract follow-ups. |
| Codex adapter commands/process | =Controls= / =Ledger= structs, bind string and status JSON files, atomic writes and run lock | Daemon RPC contracts cover these calls; file/control protocols remain separate follow-ups. |
| Machine consumers of CLI output, including TRAMP and Claude mod | Clap arguments, exit codes, JSON/text printers and handwritten parsers | Reuse generated public DTOs where output is identical; separately inventory wrappers, adapter status and machine-output stability. |
| Nix producers/runtime consumers | Nix manifest/build-spec emitters and validators, Rust deserialize/validation types | Separate schema/build-time validation follow-up; do not turn configuration files into RPC. |
| Persisted history/audit and shared locks/leases | Versioned Serde records, JSONL events, flock and filesystem publication/cleanup rules | RPC contracts cover exposed records and compatibility; retain persistence/lifetime protocol documentation separately. |
| Frontend/payload terminal and exec stdio | PTY/stream bytes, terminal escape sequences and SCM_RIGHTS | Preserve byte streams; generated handshake/control contracts end at the stream transition. |
| External Codex App Server and Claude integration APIs | Upstream protocols with handwritten adapter JSON parsing and partial local types | Generate/import upstream types where feasible as separate adapter work; do not invent a Goblins-owned upstream contract. |
| Bubblewrap, pasta, Nix, Git and emacsclient | External command arguments/output, ready/PID files or pipes, exit status | Keep bounded handwritten integration adapters and tests; external format changes are independent migrations. |
| Docker/Nix daemon sockets exposed to sandboxes | External service protocols plus local exposure/grant policy | No replacement schema in this plan; test exposure/authority and compatibility. |
| Parent/child lifetime and cancellation | Signals, pidfds, parent-death handling, EOF, reaping and lock release | Preserve and test behavioral invariants; no generated JSON type substitutes for them. |

Supervisor worker channels and daemon messaging queues connect threads, not processes. Their Rust enums and authority boundaries remain; generated DTO conversions belong at the process boundary.

* Validation and delivery

Use the Git-backed =nix develop=. Select affected features with =just test-plan --changed master= or =just test-plan --paths FILE...= and keep =tests/features.toml= current. Run one test runner per checkout/cache across the raid. Use fast unit/compatibility checks during implementation; rerun checks affected by a fix rather than repeatedly running unrelated integration suites.

Before merging, =just test-merge= must pass on the final candidate. Report failures and environment-dependent skips explicitly; focused passes and reviews do not replace the merge gate. Preserve isolation for lifecycle, authority and cleanup tests, and do not hide failures with weakened assertions or retries. The user retains final validation and the merge decision.

The pre-fixture-reduction candidate passed the full merge gate. Subsequent fixture and documentation/tooling reductions require a new final gate before merge; consult current test logs and the latest review rather than treating historical chunk reports as evidence for the current candidate.
