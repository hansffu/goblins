#+title: Goblins agent integration specification
#+date: 2026-10-13

* Scope

[[file:../adr/0001-daemon-inboxes-for-agent-communication.md][ADR 0001]] defines the architecture: daemon-owned inboxes with notify-then-fetch
communication, native agent terminals, inherited authentication, and sandbox-only
integration configuration. [[file:../adr/0009-sandbox-owned-codex-delivery.md][ADR 0009]] supersedes the Codex terminal
wakeup driver with a sandbox-local App Server adapter. Claude's existing native
notification monitor remains unchanged. Ownership, grants and teardown rules in
[[file:DAEMON.org][DAEMON.org]] continue to apply.

* Native configuration and delivery driver

=mkCodexGoblin= takes the same options as =mkGoblin=, plus =codexConfigDir=
(default =$HOME/.codex=), =codexSettings= and the native =pkg=. It shares the
entire Codex directory with the goblins its raid owner runs alongside it. Generated hooks/configuration and the
Goblins spawning, messaging and package-request skills are immutable mounts under
=/etc/codex=; no host settings are
rewritten. Native credential refresh retains the normal writable auth mount.
Configured MCP servers are preserved by default. The optional
=filterUnavailableMcp=true= behavior is an explicit compatibility option. Its
default description is =Codex running in a Goblins sandbox=.

=mkClaudeGoblin= follows the same contract with =claudeConfigDir=,
=claudeSettings= and =pkg=. Its immutable managed settings and enterprise
skills live under =/etc/claude-code=, while the selected Claude state directory
is writable and shared with the Claude goblins a raid owner runs. Its default description is =Claude Code
running in a Goblins sandbox=.

The trusted =mkGoblin.integration= setting selects the delivery profile; the
supported values are ="codex"= and ="claude"=, with =null= for ordinary shells.
The native package, mounted hooks and notifier are supplied by the matching
builder. Goblins a raid owner runs use the daemon's current manifest, never an
agent-supplied one.

Codex requires version 0.162.1 or newer. The launcher creates the private
=/tmp/goblins-codex= directory, starts App Server on its explicit Unix socket,
starts =goblins-codex run=, and connects the native TUI through the adapter's
local pass-through socket with =--remote=.
The socket is outside shared =CODEX_HOME=. Native utility subcommands retain
normal argument handling. Authentication mounts, managed skills, user hooks,
MCP filtering, images, attachment and Goblins' outer policy remain native.
The launcher also applies CLI configuration and the selected native profile to
App Server, since remote thread creation forwards only selected config fields.
Profile values are parsed as TOML and passed as arguments without shell evaluation.
Native exit preserves its exit code and terminates both helpers.

Only the managed SessionStart hook is installed for Codex. It reports the exact
=session_id= without blocking a turn or consuming inbox work. Codex 0.162.1
runs this hook when the first turn starts. The adapter therefore also passes
through the native WebSocket connection unchanged and captures thread IDs only
from successful native =thread/start=, =thread/resume= and =thread/fork=
responses for foreground requests. Codex's hidden title/recap threads and
background-task requests share that connection but never replace the binding.
Foreground request identities follow the pinned native protocol; unfamiliar
string identities do not authorize a switch. This binds empty terminals and switches before an inbox arrival,
without selecting threads by name or recency. The active native ID guards
against a late compaction hook from the previously selected thread. Repeated
compaction hooks keep the same binding. SubagentStart does not rebind the native terminal. The
adapter subscribes by resuming only a proven loaded thread, without overrides,
and ignores other threads. Native approval and user-input requests are never
answered by the adapter. A newly created thread can temporarily lack persisted
history; observer binding retries while native global status events remain
available.

The adapter polls =inbox.status= every 500 ms, including outstanding claims.
It neither fetches nor acknowledges messages. It submits only:

#+begin_quote
Check your Goblins inbox and process the next item.
#+end_quote

Submission uses experimental =thread/queue/add=, never =turn/steer= or PTY
input. App Server executes the reminder at an idle boundary, after busy turns,
including failed/interrupted turns. =thread/queue/start= handles an idle queued
reminder when automatic scheduling has not started it. The agent uses the same
Goblins messaging skill and CLI to fetch, reply and complete work.

Claude still registers its driver before launch, exports the epoch to its hooks, and runs =goblins integration watch --delivery notification= in its native plugin monitor, which turns each notification into a turn without editing the composer. The monitor appends a wake marker naming the inbox head (or claim) to the fixed prompt, =[goblins-inbox-wake ID]=, so the Goblins mod can label the row; it never carries a body. While the monitor process runs, the Stop hook reports =active=, so the daemon settles =ready= and its notifier, not a Stop continuation, delivers and retries what is pending; without the monitor, Stop continues as before. Claude's daemon control and communications-log behavior is unchanged ([[file:../adr/0015-claude-code-mod.md][ADR 0015]]).
Codex does not register, tick, or invoke the daemon terminal-delivery path.
The trusted =integration="codex"= configuration marker remains solely for
operation-notice eligibility.

* Inbox contract

All agent messages and replies pass through the host daemon. The authenticated
sandbox endpoint supplies sender identity. An agent can send to running or
starting members of its unpaused raid (see Raid routes below); there are no
parent or descendant routes since [[file:../adr/0014-raids-replace-the-ownership-tree.md][ADR 0014]]. It can reply to the sender of a claimed message while a send between
them would still be authorized. Other branches remain unavailable. Host send
always uses sender =host=.

Each message contains immutable daemon-issued message and conversation IDs,
sender/recipient IDs and captured display paths, body, creation time/sequence,
state and claim generation. Conversation IDs provide correlation, not authority.
Bodies are UTF-8 text of at most 8 KiB. Message states are queued, claimed,
completed and failed.

=inbox.next= claims the oldest item. Only one claim may be outstanding; repeated
fetches return that claim until it is replied to, completed or requeued. Requeue
invalidates the previous claim generation. Reply atomically completes the claim
and queues a correlated reply to the original sender. Recipient exit fails
queued/claimed messages. Empty fetches are receipts too.

Mutations use operation keys. Retrying identical arguments with the same key
returns the original result, even after a name is reused; changed arguments
conflict. A new operation needs a new key. CLI omission generates a fresh key
and prints it before submission. Exit 0 means accepted, 1 means known failure,
and 2 means uncertain outcome. An accepted send does not mean consumed.

File input is read in the sending CLI's own namespace and transmitted as text:

#+begin_src sh
goblins send scout --file /tmp/task.txt --key setup-1
goblins send scout --message "my message"
goblins reply MESSAGE_ID --claim-generation N --file /tmp/reply.txt
#+end_src

Exactly one of =--message= and =--file= is required. =--file -= reads stdin.
The daemon does not open a caller-supplied pathname. The recipient never needs
access to that path, and deletion/change after acceptance cannot change the
queued body. Binary attachments and general file transfer are outside scope.

** Raid routes

Raids ([[file:../adr/0008-raids.md][ADR 0008]], [[file:DAEMON.org::*Raids][DAEMON.org]]) add one route. Authorization uses
only membership the messaging worker has recorded in the communications log,
never the controller's copy: the controller sends raid events with each
=Work::Call= and =Work::Sync=, and the worker records them before handling
the call they arrived with, applying each to its logged view once written.
A join or role change therefore authorizes nothing until it is in the log;
removals apply even when their event cannot be written. =mailbox::Directory=
carries no raid data.

- A sandbox may send to a live member of its logged raid by agent name or ID;
  the ambiguity error covers name collisions. Roles are never matched. There
  is no =parent= alias; host routing is unchanged. A paused raid refuses with
  a warning and a resume notice later (see DAEMON.org, raids replace the
  ownership tree).
- A reply is allowed when the original sender is the host, or when both are
  in the same logged, unpaused raid. Otherwise it fails with -32009 "not allowed: 'SENDER' is
  no longer in this goblin's raid" and changes nothing: the claim stays
  outstanding for completion or requeue.
- Delivered messages stay with their recipient. =messages.get=, inbox
  operations and conversation reuse do not depend on raid membership.
- =message.accepted= data (=change=) gains =route= (="raid"= when logged raid
  membership was the only authorization, else ="tree"=) and =raid=, the raid
  ID or null.
- Raid events are =raid.created {raid,name,owner}=, =raid.joined
  {raid,session,role}=, =raid.role {raid,session,role}=, =raid.left
  {raid,session,reason}= and =raid.dissolved {raid,reason}=, with =actor= set
  to the initiator (a session or =host=) and =sessions= to the affected
  members, so =--session= filtering shows an invited or dissolved member its
  own events. They do not count against the auxiliary-event limit.
- A write failure sets =audit_failed= and freezes messaging as for any event.
  A capacity failure sets =raid_audit_failed=: removals still apply, later
  additions are neither recorded nor applied, and raid-routed sends and
  replies fail with -32009 "raid membership could not be recorded" while tree
  routes keep working.

* Codex delivery ownership and retries

At most one reminder is outstanding for each bound thread. Arrivals coalesce.
Before sending, the adapter atomically persists =clientUserMessageId= and its
attempt count in a sandbox-local ledger. Successful replies add the queue ID.
Reconnects reconcile all queued submissions and bounded recent thread items;
=userMessage.clientId= correlates accepted reminders, including already-started
turns. A missing acknowledgement never implies rejection. Unresolved ownership
suspends further submissions and appears in local diagnostics, leaving inbox
contents untouched. Local resume resets the attempt limit but never discards
uncertain ownership.

Without inbox-head/claim-generation progress, submit at most three reminders,
at least 30 seconds apart. Progress or explicit local resume resets the budget.
Failed and interrupted reminder turns remain eligible for pending inbox work;
the adapter never independently retries the previous human task.

=pause= prevents new reminder submissions; already accepted App Server queue
work retains its native ownership. =resume= allows new reminders and resets the
retry budget. These controls live inside the sandbox, accessible from the host:

#+begin_src sh
goblins exec chief -- /run/goblins/bin/goblins-codex status
goblins exec chief -- /run/goblins/bin/goblins-codex pause
goblins exec chief -- /run/goblins/bin/goblins-codex resume
#+end_src

The status file includes binding, activity, pause, ledger and diagnostic fields.
Adapter failure preserves manual inbox commands; stale activity expires at the
daemon. Claude retains =goblins integration status/pause/resume NAME= and its
existing turn-boundary hooks.

* Provider-neutral activity

Sandbox-only =goblins set-state STATE= calls =sessions.set-state {state}=.
States are =unknown=, =idle=, =working=, =waiting-input= and =waiting-approval=.
The endpoint selects the reporting sandbox. Target identifiers, unknown fields,
invalid states, host reports and reports after running ends are rejected.
Session snapshots add =agent_state=, default =unknown=, independently of the
existing lifecycle =state=. No last-turn outcome field is added.

Snapshots also carry =agent_state_since=, the Unix time in milliseconds when =agent_state= last changed (absent until it first does), and =inbox=, the number of messages queued for the goblin. The messaging worker reports the queued counts to the controller whenever they change, so a send, claim or failed delivery republishes the snapshot. The workspace sidebar shows both.

Accepted reports refresh a daemon-owned monotonic timer. After 30 seconds
without a report activity becomes unknown; stopping clears it. State subscribers
receive updates only when visible activity changes, not on equal heartbeats.
The adapter reports transitions immediately and refreshes every ten seconds,
independently of provider RPC delays. App Server idle maps to idle; active work
to working; native waiting flags map to waiting states, with user input taking
precedence over approval. Unbound/unavailable/error states map to unknown.

Claude has no App Server to observe, so the daemon derives its activity from the integration hooks it already receives, kept beside (never inside) the wakeup lifecycle. SessionStart reports idle and UserPromptSubmit working; Stop reports working when it continues into the inbox and idle otherwise; StopFailure (an API error) reports idle. PreToolUse for AskUserQuestion or ExitPlanMode, Elicitation, and elicitation notifications report waiting-input; PermissionRequest and the permission_prompt notification report waiting-approval. PostToolUse, PostToolUseFailure and ElicitationResult return to working only from a waiting state, so a late tool end never revives a settled turn. Claude fires no hook when a person interrupts a turn; the Goblins mod reports the interrupted turn's end as an idle_prompt notification at once, and without the mod Claude's own idle_prompt, about 60 seconds later, settles it to idle. Activity-only hooks change no wakeup state and write no communications-log event. Each =integration.check= and the plugin monitor's =integration.tick= return =agent_state= for Claude, and the controller applies it as a report: the 500 ms monitor ticks are its freshness heartbeat, so activity expires once Claude and its monitor exit.

=goblins status= and Emacs overview, sidebar and details show this activity.
Older snapshots display unknown. Goblins permission badges remain separate from
Codex native waiting flags; informational activity never authorizes a grant.

* Operation completion notices

Package grants, Docker attachment and dev shell refreshes are Goblins-owned
operations: =permissions.request= returns one terminal result to a CLI that
blocks until host approval and execution finish. An agent can yield while that
command still waits (for example in a background terminal), and nothing used
to resume it when the result arrived, since wakeups follow inbox state only.
A developer/QA raid stalled this way after =goblins enable-docker= until the
user asked for status.

Each terminal outcome of a sandbox permission request therefore also queues
one daemon-authored notice in the requester's inbox. The Codex queue adapter or Claude monitor delivers it like any other inbox
item. Each driver applies its own pause and retry policy. Operations the sandbox runs itself,
including arbitrary shell processes, get no notice; nor do =flake.run= and
=devshell.diff=, whose results are only useful to their waiting command.

- Identity :: a notice has sender =goblins= (neither a session nor the host)
  and a =message.operation= object ={request,kind,subject,status,message}=.
  =request= is the daemon-issued permission request ID that the CLI also
  prints. =status= is the final record state: =ready=, =denied=, =failed=,
  =withdrawn= (connection closed before a decision) or =cancelled= (session,
  payload, worker or daemon stopped). =message= is the sandbox-facing text,
  never the host diagnostic. Each notice starts its own conversation.
- Semantics :: a notice is sent for every terminal outcome, also when the
  waiting CLI received the same result and the agent is still working. The
  daemon cannot tell whether the model read the CLI output, and suppressing
  the notice for an active agent would lose exactly the backgrounded case at
  its next idle boundary. Codex queues a reminder after the current turn;
  Claude uses its monitor notification flow (a Stop continuation only while its monitor is not running). An agent that already handled the result
  just completes it. =messages.reply= to a notice fails with -32009 and leaves
  the claim outstanding; complete or requeue it instead.
- Eligibility :: notices go only to sessions whose trusted configuration has
  an integration (=codex= or =claude=) and that are live when the outcome is
  recorded. Others get a logged outcome with =notice: null= and =undelivered=
  set to ="no agent integration"=, ="recipient not running"=,
  ="mailbox capacity reached"=, ="mailbox audit unavailable"= or
  ="communications log capacity reached"= (the log has room for the outcome
  but not for the notice and its reserved claim and completion). A notice
  queued before its recipient stops fails with the rest of that inbox.
- Delivery :: the controller queues =operation.requested=,
  =operation.decided= and =operation.completed= events in an ordered outbox
  that rides on every messaging =Work::Call= and on =Work::Sync= while it is
  nonempty, exactly like the raid outbox, and is cleared only once
  =try_send= accepts it. The worker records them before the call they arrive
  with. Completions are never dropped: while 1024 events are unaccepted, new
  permission requests fail with -32010. Orderly daemon shutdown records still
  pending operations as =cancelled= ("daemon stopped") without notices and
  hands the outbox over before the messaging worker closes.
- Duplicates :: the worker remembers the last 1024 requests whose outcome it
  handled; the controller resends only a batch the worker never accepted, so
  duplicates can only be recent. A repeated completion records
  =operation.duplicate= and queues nothing, and a repeated request record is
  ignored. A notice never resubmits or retries
  the operation.
- Status :: =inbox.status= adds =operations=, the caller's own unfinished
  operations as the log records them: ={request,kind,subject,state}= with
  =state= =pending= (awaiting a decision) or =running= (approved or
  automatic, executing).

The communications log distinguishes the phases of a wait. Approval wait runs
from =operation.requested= (data ={request,kind,subject,reason,automatic}=,
actor the requester) to =operation.decided= (={request,approved}=, actor
=host=, or =goblins= for an inherited approval). Execution wait runs to
=operation.completed= (={request,kind,subject,status,message,notice}=, actor
=goblins=), which also queues the notice. Notification delivery then appears
for Claude as =integration.wake_attempt=, =integration.wake_result= or a Stop
=integration.hook= continuation. Codex submission diagnostics remain local to
the adapter. The agent's response is logged as
=message.claimed= and =message.completed= for the notice ID. All carry the
requester in =sessions=, so =--session= filtering shows them. Requested and
decided events count against the auxiliary-event limit; outcomes do not, so
they are recorded after Claude ticks and hooks have spent it; Codex queue
bookkeeping does not spend daemon integration audit capacity.

* Settled protocol

JSON-RPC framing, endpoint authentication and bounded connections are unchanged.
Initialize advertises =agent-inbox-v1=, =agent-integration-v1=,
=agent-activity-v1= and host-only
=communications-log-v1=. Integration calls are authorized against the trusted
profile and the caller's own sandbox. Host controls resolve explicit sessions.

| Method | Parameters/result |
|--------+-------------------|
| =messages.send= | ={key,to,body,conversation?}= -> accepted message |
| =messages.get= | ={message}= -> visible message record |
| =inbox.status= | ={}= -> queued, claim, head identity, revision, audit_failed, raid_audit_failed, unfinished operations, integration health |
| =inbox.next= | ={key}= -> message and claim_generation, or null message |
| =messages.reply= | ={key,message,claim_generation,body}= -> reply plus completed original ID |
| =inbox.complete= | ={key,message,claim_generation}= -> completion |
| =inbox.requeue= | ={key,message,claim_generation,reason}= -> new generation |
| =sessions.set-state= | sandbox-only ={state}= -> accepted; endpoint identity, running sessions only |
| Claude =integration.register= | ={driver,key}= -> epoch; same registration key is retryable |
| Claude =integration.check= | ={epoch,key,event,active?,tool?,notification?}= -> continue decision, agent_state and integration status |
| Claude =integration.tick= | ={epoch}= -> notify decision, optional terminal revision/delivery result, agent_state, integration status |
| Claude =integration.status= | own ={}=, host ={session}= -> epoch, activity, health, attempts |
| Claude =integration.pause/resume= | host-only ={session}= -> updated integration status |
| =communications.list= | host-only ={after?,limit?,session?}= -> events, cursor, latest, resolved session |

Claude's turn-boundary hook events are SessionStart, UserPromptSubmit and Stop;
StopFailure, PreToolUse (AskUserQuestion/ExitPlanMode), PostToolUse,
PostToolUseFailure, Elicitation, ElicitationResult, PermissionRequest and
Notification only report activity. Codex uses only
SessionStart for exact thread binding. No message body or
arbitrary PTY input is accepted by integration methods. Terminal evidence is
supplied privately by the controller, not trusted from the sandbox. Epochs
reject stale reports; a second registration cannot steal a running driver.
The first baseline does not implement driver replacement or subscriptions.
A later native driver can extend this boundary in its own scoped change.

Bounds: 16 live sessions, 8 connections per sandbox, 64-KiB message requests,
256 unresolved messages per inbox, 4096 messages and 16384 operation receipts
per daemon. Auxiliary lifecycle/retry audit events are capped at 16384. Host
log pages contain at most 100 events and 512 KiB. Terminal parsing has no
scrollback and bounded dimensions; terminal consumers retain existing limits.

* Communications log

The host-private append-only JSONL file is
=STATE/communications-INSTANCE.jsonl=. It survives session cleanup and daemon
shutdown, without promising restart recovery or power-loss/fsync durability.
Mailbox transitions are appended before acceptance/publication. Audit errors
freeze new messaging mutations and wake attempts, leaving terminal control
available. Already committed retry receipts remain recoverable.

Events include session identities/ancestry, accepted messages, claims, replies,
completion/requeue/failure, duplicate operation retries, integration registration,
hook decisions, notification attempts/results, raid membership changes and the
lifecycle of sandbox permission requests (see Operation completion notices). Exact message contents are
available for host verification; credentials and unrelated terminal output are
not logged. Human-readable output escapes terminal control characters.

#+begin_src sh
goblins communications-log --session chief --json
goblins communications-log --session chief --follow
goblins communications-log --log /path/communications-INSTANCE.jsonl --json
#+end_src

Live follow polls with a sequence cursor, verifies the daemon instance, and
resolves the selected session to an immutable ID. Offline selection supports an
exact session ID or captured path from session-start records. Offline reads
validate file size, complete JSONL records, instance and sequence continuity.
Offline =--log= cannot be combined with =--follow=.

* Verification

The default suite uses fake agents, synthetic credentials and native local UI
commands that do not submit model prompts. It covers inbox semantics and scope,
private sender-local files, hook continuation, idle/working transitions, input
ownership, bounded retries, audit failure, native mounts, and attachment.
No automated test requires a paid Codex subscription. Native protocol tests use
synthetic credentials and a scripted provider on loopback. Adapter tests cover
coalescing, retry limits, uncertain acknowledgements, reconnect reconciliation,
failed/interrupted turns, thread identity and API/audit failures. Sandbox tests
cover drafts, native images, parent/child isolation, detached processing, native
exit and teardown. Activity tests include real daemon state subscriptions.

Build the adapter before running the native proxy smoke tests:

#+begin_src sh
cargo build -p goblins-codex
python3 -m unittest discover -s tests -p test_codex_native.py
GOBLINS_TEST_CODEX=1 python3 -m unittest discover -s tests -p test_codex_config.py
#+end_src

The terminal tests require the dev shell's =pyte= package. Native credentials
are synthetic and the provider is scripted locally; account keys are removed
from the native smoke-test environment.

The real counting game is a manual acceptance exercise. Do not add a reusable
live-game script, unittest or Nix check. Launch an isolated daemon with the real
Codex profile and inherited authentication, then enter the task in the native
TUI. Preserve the communications log and inspect the resulting conversations.

The parent must create a separate child goblin, send setup through the daemon,
and make exactly ten individual guesses. Wait for each correlated reply before
sending the next guess, including after a correct guess. Each child response
is correct/too high/too low. After reply ten, request the actual number and
report the result. Setup and reveal exchanges are separate from the ten guesses.

Use a salted commitment to make changing the number detectable: the child
chooses NUMBER and a fresh 32-byte salt encoded as lowercase hex, stores them
privately in its own /tmp, and initially replies with SHA-256 of UTF-8 bytes
=goblins-number-v1\nNUMBER\nSALT\n=. Reveal NUMBER and SALT only after guess ten.
Verify the commitment and every comparison from the communications log.

During the trial, attach/detach the child without consuming its inbox, and
include a deliberately delayed exchange after an empty Stop check. Inspect
actual tool calls for built-in delegation, transcript reads, shared-file
handoffs or terminal-mediated messaging. Shared native configuration/history
means isolation alone cannot prove honest behavior; record the evidence and
any limits rather than claim stronger guarantees than the run demonstrates.
