metadata notifier alongside the native CLI. SessionStart/UserPromptSubmit/Stop

transport settings in =config.toml=. Native =codex mcp list= also returns
plugin-provided servers. For those, an invocation override containing only
=enabled=false= created an invalid transport and prevented Codex from starting.

* Open networking and Codex startup (2026-09-20)

=mkGoblin= now defaults =allowedDomains= to =null=, matching the agent-sandbox
library's open-internet behavior. =[]= explicitly disables networking. There
is no domain allowlist or HTTP/TLS proxy. Domain filtering and explicit host or
published-port mappings remain unsupported.

The daemon runs the library's =pasta= dependency per session. A private keeper
owns the network/user namespaces; the trusted helper receives pinned namespace
descriptors and validates their ownership before entering them. Its existing
source/payload mount and user namespaces remain separate. The payload receives
DNS configuration, without namespace handles or host network sharing. The
transport is IPv4, with host loopback mapping and automatic port publishing
disabled. Children inherit the configuration with independent network namespaces.

The Codex wrapper checks native effective MCP configuration and disables local
MCP entries whose executables are absent using invocation-only overrides. It
does not edit shared host configuration. =filterUnavailableMcp = false= restores
unfiltered native startup. Codex's CLI cannot express dotted server names through
these overrides; unavailable entries with such names are reported and retained.
The docs also consistently refer to the agent-sandbox library by name.

returned 401, and =auth.openai.com/oauth/token= returned 405. Curl exited zero
for each, verifying host-forwarded DNS, outbound TCP and certificate-checked TLS.

* Manual daemon inbox foundation (2026-09-19)

The first implementation slice on =feat/agent-integration-poc= adds daemon-owned
inboxes and =send=, =reply= and =inbox= commands on host and sandbox CLIs.
The daemon authenticates senders from their endpoint, restricts sandbox routing
to parents/descendants and direct replies, and owns message contents and claims.
Sending a file reads it in the sender's filesystem; no file pathname crosses
the messaging protocol. Host sends and replies use a real =host= inbox.

The serialized mailbox worker performs audit writes outside the controller's
event loop. Successful mutations have audit records before becoming visible.
Identical operation keys replay their original result; changed arguments
conflict. Replies atomically complete the original claim and queue a response.
Requeue increments the claim generation. Message, inbox, receipt and audit
capacity are bounded, with capacity reserved for completing existing work.
Uncertain audit writes disable mutations without disabling terminal management.
Private JSONL logs preserve accepted bodies and state transitions, and host
=communications-log= supports subtree filtering and polling follow.

ignored; formatting and workspace/all-target Clippy with warnings denied passed.
The production Nix build and *25 Python tests* covering messaging, daemon,
ownership and responsiveness passed. Real sandbox testing confirmed different
contents at the same =/tmp= pathname on host and sender: the recipient received
the sender's contents after source deletion. Tests also cover authenticated host
send/reply, duplicate acceptance, forbidden routing and impersonation, private

=help COMMAND= expose that command tree. Bash, Fish and Zsh scripts are generated

locations. =completions SHELL= provides manual setup. The scripts are static;
live session names are not completion candidates.

* Pre-merge review fixes

Review found and fixed two daemon lifecycle races and a startup-bind race:

- Worker completion is recognized only after its result channel is disconnected
  and drained. A final status arriving after an empty poll is preserved. A worker
  that exits without its final event leaves a failed session record, not a
  permanently running/stopping record.
- Progress must belong to the live pending grant. Queued mounting/publishing
  events cannot restore a permission already cancelled by session stop.
- Startup binds now validate and mount the same opened object. Source handles
  are passed explicitly through the launcher/helper and consumed by Bubblewrap's
  descriptor bind operations. Host descriptors do not reach the payload. The
  changed private launcher contract is helper API 2 (=READY2=); JSON-RPC is API 1.

The synthetic two-sandbox reproduction on baseline =9fffbb5= failed its safety
assertion: after sandbox A replaced a writable shared child with a symlink to
private daemon state, sandbox B received =host.sock=. No real secrets or host
control operations were used. The fixed build retains the original inode and
live host updates while hiding the synthetic private marker/control socket.

* Daemon milestone (API 1, initial frontend at 52feceb)

Implemented on =feature/daemon-protocol= from =eb3276f=, following
[[file:docs/specs/DAEMON.org][DAEMON.org]]. The ordinary-user Rust daemon owns simultaneous sessions,
requests, approvals, package grants and PTYs. Both approval frontends now use
the private host API; sandbox requests go directly to their endpoint-scoped

The exact API, limits, retention, duplicate handling, terminal lifetime and
manifest/helper compatibility choices are recorded in DAEMON.org's
implementation contract. Current operational instructions are in

*** Explicit limits

Controller/daemon restart recovery is *out of scope*: no reconnect, state
restoration or survival across controller restart. Normal shutdown cleans session
roots/directories; SIGKILL can leave them. A daemon, Emacs integration, full TUI,
multiplexing, orchestration, notifications, live file/network grants and real-agent
credentials are not implemented.

Package grants remain additive. Individual store paths can become readable
before atomic profile publication; partial failure kills the session and cannot
erase data already read. No GC stress test, exhaustive syscall/security audit,
resource quota, revocation, development setup-hook activation or other-platform
validation is claimed. Arbitrary payload code execution is expected.

Cancellation terminates owned Nix clients, not the host Nix daemon or shared
build jobs. Slow filesystem/kernel I/O can still delay cleanup; no hard real-time
or resource-exhaustion guarantee is made. The slow-build regression uses a
trusted test substitute, while ordinary grants use actual pinned host Nix.

The =agent-sandbox-baseline= output was successfully built with =allowNix=false=

** Hardest-gate observations

The first variant retained a host-source descriptor and entered the target
mount namespace. =setns= succeeded, but =open_tree= failed with =EINVAL=.
The source mount was outside the current namespace. This failure was not
hidden or replaced with a copied-store design.

The working helper retains a private source mount namespace owned by user
namespace A, and the target mount namespace owned by its child B. It clones and
hardens in the source namespace, then switches to the target and attaches by
FD. Ownership is checked, not inferred from a shared UID. At steady state the
helper's effective capability mask is =0000000000240000=, exactly
=CAP_SYS_ADMIN | CAP_SYS_CHROOT= in A. Payload capability sets, including the
bounding set, are all zero.

** Positive evidence

- The complete =jq= runtime closure was mounted. Three previously absent store
  objects were added on this machine: the =jq= bin output, its library output,
  and the Oniguruma library. Other dependencies were already in the initial
  Bash/Python closure. Tests checked every closure path exists and every
  individual store mount has =ro,nosuid,nodev= flags.
- The absolute-interpreter =script-tool= printed =script-interpreter-ok= using
  Dash from a newly granted store path.
- =data-tool= printed =runtime-data-ok= from a distinct top-level store file,
  proving both directory and regular-file store objects mount successfully.
- A fresh =/bin/sh= child found and ran the newly granted =jq= through the
  inherited stable profile PATH.
- A second sandbox remained unable to see the first session's =jq= output.
- =goblins-request= crossed the intentionally allowed pathname Unix socket,
  received =denied= / exit 1, then =ready= / exit 0 after a host-controller
  decision. Approved realization uses the pinned host catalog.
- A foreground host-PTY smoke test exercised the real =terminal.py --demo=
  presentation with synthetic host-terminal =approve= input. It displayed
  =original shell 2=, =jq-absent=, the request, =ready=, =same shell 2=, and
  successful JSON output. =:status= reported =jq= and =:quit= cleaned up.
  This is an automated terminal smoke test, not a claim of a separate human
  authentication trial.

The =jq= catalog initially selected multiple Nix outputs (=bin= and =man=),
which correctly failed the controller's single-output check. The catalog now
explicitly requests =jq^bin= and follows that output's runtime closure.

  path:.#runtime

Recorded full suite: *9 Python tests passed* (six integration scenarios and
three protocol scenarios). The Nix helper build and a local =cargo test --offline=
run each passed the Rust store-name validation test. Rust formatting and Python
syntax checks also passed. The real foreground terminal flow was exercised
separately as described above.

** Remaining limits and untested claims

- No implementation blocker remains for this package-only experiment on the
  tested Linux/NixOS machine. Other architectures/kernels are not validated;
  the seccomp program explicitly requires x86_64.
- No real agent, credentials, network authentication, or credential-sharing
  policy was tested. These remain separate from package grants.
- Root references were queried and normal/crash cleanup observed. No global
  host GC was forced, and no claim is made about a simultaneous GC stress run.
- Read-only flags and mutation probes were checked. There was no adversarial
  kernel exploit testing or exhaustive syscall/security audit.
- Closure completeness means Nix's recorded runtime references. Arbitrarily
  discovered plugins, unrecorded data, setup hooks, and developer environment
  activation remain outside this implementation.
- There are no resource quotas, durable retries, request scheduling, crash
  reconciliation, revocation, or graceful terminal job control. An agent can
  exhaust resources or stall its own request flow.
- Ordinary package contents are readable; arbitrary code execution is expected.
  Procfs can reveal kernel/hardware information. Mount access does not provide
  a VM-equivalent confidentiality boundary.
- Direct store paths become visible one mount at a time. Profile publication
  is atomic, but the whole grant is not. Failure kills the session and cannot
  erase data already read.
- Abrupt controller death can leave session directories and GC roots. Cleanup
  is manual after verifying the crashed session is gone; no service was added.

** Interactive Fish follow-up

At the user's request, the lower Herdr pane was switched to a real Fish shell
using agent-sandbox =mkSandbox= with =commonTools ++ [ pkgs.fish ]=. The flake output
is =fish-shell=, and =fish_terminal.py= supplies a disposable workspace and the
actual terminal. The original live-grant controller remains separate.

The pinned build succeeded. A sandboxed Fish command probe reported Fish 4.7.1
and found every commonTools executable. It confirmed no Nix daemon path, no
=nix= command, and no unrelated Rust helper store output. Effective capabilities
were zero and =NoNewPrivs= was 1. Agent-sandbox retained a nonzero capability bounding
set; do not apply the custom live-helper's zero-bounding-set claim to this shell.

The interactive Herdr pane reached =user@sandbox ...>= and was checked with
normal command input and Ctrl-C. The configuration denies Unix sockets, permits
no network domains or host ports, and supplies =jq= at startup. The shell is
not yet wired to the live approval socket. These checks do not amount to a full
security audit of agent-sandbox's filesystem exposure or networking implementation.
